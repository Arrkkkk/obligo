## Phase 3 — Ingestion, Storage & Segmentation (complete)

Phase 3 (Ingestion, Storage & Segmentation) is complete and verified, locally and in CI, against real infrastructure (no mocks) — all four blueprint §21 acceptance criteria Met or explicitly, permanently deferred:
- **Presigned upload flow (§11.2)** — `sources` table with RLS from creation, upload-intent/commit against real Supabase Storage, SHA-256 dedup-on-reupload. Real finding: Supabase's signed-upload token ignores a caller-supplied expiry (always ~2h, not blueprint's 5 min target) — verified live that a leaked/replayed URL still can't do anything once the legitimate upload lands (`upsert:false`, no read scope, path-bound signature), so the real exposure is narrower than it first looked (a pre-upload race on an abandoned intent); bounded server-side to a 30 min staleness cap, not "solved."
- **File-security hardening (§11.6)** — magic-byte sniffing, size cap, PDF active-content rejection (JS/launch actions/embedded files), a three-part decompression-bomb guard (page count ≤500, 200:1 expansion ratio, 10s timeout), and server-side SHA-256 recomputation (a deliberate deviation from blueprint's sync/async two-tier split — done synchronously up to the full 50MB cap instead, since no async-worker infra exists yet). All proven with real PDFBox-generated and downloaded malicious/benign fixtures — including a real page-count-cap gap (blueprint's own literal "600-page file" case) found completely untested and closed during the Phase 3 sign-off pass, not assumed covered by the byte-size cap it was previously conflated with.
- **Tenant isolation ported to apps/brain (§10.9)** — the first Python-side Postgres access, proven with the same rigor as the Java-side suite (identical `pg_backend_pid` across tenant contexts, zero leakage) plus one write-path case Java's own test doesn't cover. `contextvars.ContextVar`, not `threading.local` — FastAPI's asyncio concurrency model means a naive port would leak one request's `org_id` into another's.
- **PyMuPDF text/layout extraction, offsets derived by construction, not post-hoc matching** — `page_text[char_start:char_end] == text` holds by construction for every segment, because the persisted text is literally what produced the offsets. Real, documented, not-fully-solved limitation: round-trip correctness is guaranteed; reading-order correctness on genuinely multi-column layouts is not (PyMuPDF's block order is a position heuristic, demonstrated on a real two-column fixture and asserted so a future fix changes the test loudly).
- **PyMuPDF is AGPL-3.0-or-commercial, not permissive** — confirmed against PyPI/GitHub, no permissive alternative exists with comparable layout fidelity. Accepted for the *current* deployment shape only (local/personal use — AGPL's network-copyleft clause is deployment-triggered, not distribution-triggered): **revisit at Phase 9 deployment**, not before, either confirming the AGPL obligation is acceptable or acquiring a commercial license.
- **OCR via Tesseract 5 (local dev, Apple Silicon) / PaddleOCR PP-OCRv4 (x86 Hetzner prod target)** — a deliberate dev/prod split, not a preference: PaddlePaddle ships arm64 wheels now, but current PaddleOCR still segfaults on M1-M3 Macs (a stability class wheel availability doesn't fix). Per-page (not per-document) scanned-page detection, MIN-aggregated block confidence (a deliberate choice over averaging — one badly-misread date/party-name/dollar-figure is a real correctness failure, not noise to smooth over), `LOW_OCR_CONFIDENCE_THRESHOLD` flagging proven against real degraded scans. **Revisit at Phase 9 deployment**, same footing as the PyMuPDF/AGPL decision.
- **Async segmentation via Celery on Redis** — job state lives in Postgres (`segmentation_jobs`), not a second broker, per blueprint's own stated design intent. `acks_late=True` plus a real macOS fork-safety finding (opening a network connection inside a forked child segfaults — CPython's documented limitation, not a bug here — fixed via `--pool=solo` on this machine, `--pool=prefork` on Linux CI/prod where the hazard doesn't exist) plus a Postgres-based staleness-reconciliation net for the real, verified gaps in how promptly `acks_late` redelivery actually happens under concurrent access.
- **SSE ingest-progress streaming** — apps/core polls apps/brain's existing job-status endpoint on an interval (not Postgres LISTEN/NOTIFY, which Neon's pooled connections don't support, and not a new Redis pub/sub channel), reusing the existing shared-secret-gated core→brain boundary rather than reopening it. Two real async-dispatch bugs found and fixed: this was the first async (`SseEmitter`-returning) endpoint the codebase has ever had, and `TenantJwtAuthenticationFilter` needed `shouldNotFilterAsyncDispatch()`/`shouldNotFilterErrorDispatch()` explicitly overridden to `false`, or Spring Security's own `AuthorizationFilter` failed closed on the container's internal completion/error dispatch.
- **10 varied, genuinely distinct PDF fixtures** (not padding — two new born-digital layouts and one mechanically-distinct OCR degradation, each checked for real structural variety before being added) prove offset-exactness end to end. The one permanent, explicit scope exclusion: **macro DOCX** — DOCX is rejected at upload-intent by the MIME allow-list (`{"application/pdf"}` only) before any macro-specific detection could ever run against it; revisit only if DOCX ingestion is ever added to the allow-list.

## Phase 4 checkpoints — closed

These are the closed Phase 4 checkpoints, in the order they were completed. Together they are the compiler pipeline `CLAUDE.md`'s own "Current phase" section describes as "complete and CI-verified end to end": candidate extraction → span grounding → compilation → repair → typecheck.

The Phase 4 checkpoints that are *not* here — the obligations-persistence investigation, the verifier, `ir_hash`, the eval-harness pilot, and the leading-subordinate-clause grounding fix — are still in `CLAUDE.md`, because each is still the live evidentiary basis for a row of that file's acceptance-criteria table or for work currently in progress.

### Obligation IR v1 spec

**Obligation IR v1 spec checkpoint (§21 Phase 4) — `packages/ir-spec/` written and frozen. No parser, no typechecker, no extraction pipeline code exists yet — this checkpoint is the IR's shape only.**
- **Real discrepancy found and resolved, not guessed past:** blueprint §6.2's grammar sketch lists six temporal alternatives (`BY`, `WITHIN...OF`, `EVERY`, `DURING`, `AFTER`, `BEFORE`) against §21's stated freeze of five. Resolved by merging `AFTER`/`BEFORE` into one directional `RELATIVE_TO_TRIGGER(direction, trigger)` form — keeps all six alternatives' expressive power, lands on exactly five named forms as §21 requires.
- **"Conditions only, no nested exceptions" read deliberately as "no `UNLESS`/exception construct exists in v1's grammar at all,"** not "flat exceptions are allowed, just not nested ones." The safer reading for a tool whose whole purpose is catching what a human reader would otherwise miss — a silent drop of a legal carve-out is worse than a loud refusal to compile it. **Verified mechanically, not just documented:** `grammar.lark`'s own `IF` production parses correctly while a string containing `UNLESS` genuinely fails to parse (`UnexpectedCharacters`) — there is no accidental path by which an exception clause sneaks through this grammar's own rules.
- **A real compositional gap named and given its own worked "not representable" fixture:** an obligation's `temporal?` slot is singular, so `EVERY` (recurrence) and `DURING` (its outer bound) can't compose on one obligation even though each exists individually. v1's answer: `EVERY` alone, with the outer bound left implicit to the source document's own `effective_date`/expiration — real compositional temporal expressions are v2 scope, the same footing as nested exceptions.
- **Obligor/obligee reconciled from the grammar sketch's single abstract `party` slot against the ER schema's two distinct FK columns** (`obligor_party_id`, `obligee_party_id`, a CHECK that they differ) — `PartyRef` is a two-state (`UNRESOLVED` alias / `RESOLVED` party_id) tagged union, applied as a consistent convention everywhere the typechecker, not the parser, is responsible for resolving a reference (`DateRef`, `TriggerRef` use the identical shape).
- **`packages/ir-spec/` built per §22.4's own description** ("documentation-as-artifact... the grammar, the type rules, worked examples, and the shared test fixtures both runtimes validate against") — mirrors `packages/contracts/`'s existing JSON-Schema-as-source-of-truth precedent, not a Python-only Pydantic model set Java would have no way to check itself against: `SPEC.md` (12-section narrative spec) + `grammar.lark` (frozen Lark-syntax reference, not wired to any parser) + `schema/obligation-ir.schema.json` (the canonical both-runtimes artifact) + `examples/*.json` (9 worked examples covering all 4 modalities, all 5 temporal forms, both `PartyRef` states, both underspecification mechanisms) + `examples/not-supported/*.json` (4 boundary fixtures: bare `UNLESS`, `IF`+`UNLESS` mixed, multi-level nesting, the `EVERY`+`DURING` gap).
- **Verified for real, twice** — once while drafting, once fresh from a clean directory state per this file's own standing discipline: the schema checks as well-formed JSON Schema 2020-12; `grammar.lark` loads and parses a real sample obligation with no grammar/lexer conflicts; every example's `ir` key validates against the schema with every `alias`/`raw`/`raw_text` string confirmed a literal substring of its own `source_text` (the same span-grounding discipline the real pipeline will enforce, applied to the fixtures too, not assumed). **Two real classes of self-authored bugs caught by this discipline, not by eyeballing:** four `char_end` arithmetic mistakes (hand-computed offsets that went stale after editing the sentence they were computed against), and four internal section cross-references in `SPEC.md`/the schema that pointed at the wrong section number after the document was drafted out of the order it now reads in — caught by grepping every `section N` reference and mapping each one against the real header list, not by rereading and trusting.
- **Open item, explicitly carried, not silently invented:** the closed action taxonomy (~40 verbs; blueprint names 10 examples and no more) is validated in the schema only for lexical shape, not a closed enum. Finalizing the full list is deferred to writing `apps/brain/compiler/grammar/obligation.lark` (the next checkpoint) — decide it there, against real extraction candidates, don't invent it now. The object-class taxonomy carries the identical open-item status.

### Real obligation parser

**Real obligation parser checkpoint (§21 Phase 4) — `apps/brain/src/obligo_brain/compiler/` (`grammar/obligation.lark`, `ast.py`, `parser.py`, `unparse.py`, `version.py`) written and wired to a real Lark parser, proven against `packages/ir-spec/`'s own frozen examples. Closes the action-taxonomy open item the checkpoint above explicitly deferred to this one. No typechecker, no extraction pipeline, no LangGraph code exists yet — this checkpoint is the grammar, AST, and parser only.**
- **Closed action taxonomy resolved from real language, not invented in the abstract** — 34 verbs. The PDF fixtures already in the repo were checked first and ruled out (they're Phase 3 layout-testing fixtures — an ML paper, a tax form, a definitions section — with no obligation-bearing sentences at all, a real negative finding, not an assumption); pulled real obligation sentences instead from three actual SEC EDGAR contract exhibits (a clinical-services MSA, a cross-border business-separation agreement with a DPA schedule, a transition-services agreement). All 10 of blueprint's named verbs confirmed with real quotes; 24 more derived the same way, capped comfortably under the ~40 estimate rather than padded to hit it. Verbs present in the corpus only as nouns (`REGISTER`, `AUDIT`, `CERTIFY`, `SUBMIT`, `FILE`, `DEFEND`, `INVESTIGATE`, `LICENSE`) were deliberately left out rather than forced in on vibes.
- **Four real, mechanically-verified bugs found in the reference `packages/ir-spec/grammar.lark`** while building the real one (that file was documentation-only — "not wired to any parser," per its own header — and had never actually been run through Lark this way before):
  1. `obligation` only referenced `party_ref` once despite the schema requiring both `obligor` and `obligee` — fixed with two distinct grammar rules at different positions.
  2. The bare `CNAME (" " CNAME)*` alias alternative, confirmed empirically via a minimal repro grammar (not just reasoned about), silently swallows the following `ACTION` keyword — `"Vendor DELIVER"` lexes as one alias, not two tokens — a silent misparse, not a clean failure. Fixed by requiring a quoted `ESCAPED_STRING` only.
  3. `predicate: predicate "AND" predicate | predicate "OR" predicate`, confirmed empirically, produces structurally identical parse trees for both operators with no surviving token to tell them apart — an AST built from that tree cannot distinguish `"a" AND "b"` from `"a" OR "b"` at all. Fixed with Lark `->` rule aliases.
  4. Caught by the round-trip property test itself, not by inspection: 3+-term `AND`/`OR` chains are ambiguous without grouping — a hypothesis-generated left-nested `AndPredicate` printed and reparsed came back right-nested, same flat string, different tree. Fixed by adding parenthesized-predicate grammar support and always parenthesizing compound operands in the printer.
- **`EVERY`+`DURING` composition resolved exactly as `examples/not-supported/every-during-composition.json` asked "the next checkpoint's grammar" to decide**: parses (not a hard failure like `UNLESS`, which still has no production at all — reverified mechanically against the real grammar), compiles as `EVERY` alone per `SPEC.md` section 7's documented v1 workaround, and the parser emits a real `ObligationCompositionWarning` rather than silently dropping the bound.
- **Round-trip proof against all 9 `packages/ir-spec/examples/*.json` and all 4 `not-supported/*.json` fixtures** — 6 of 9 examples match the frozen fixture bit-for-bit; the other 3 have documented, deliberate divergences (`RESOLVED` parties, `underspecified`/`missing_fields`) rather than being silently faked, since both are typechecker output and the typechecker isn't built yet.
- **Property-based tests: 2 of blueprint §19.3's 8 named properties are buildable at this checkpoint, and both are built** (round-trip, termination). The other 6 (idempotence, hash stability, typecheck soundness, temporal totality, grounding invariant, conflict symmetry) each genuinely require a component this checkpoint was told not to build (the normalizer, the typechecker, the Z3 verifier) — documented as deferred with reasons in `test_properties.py`'s own module docstring, not silently skipped.
- **New dependencies asked about before adding, not assumed:** `hypothesis` and `jsonschema` added to `apps/brain`'s dev dependency group (alongside `lark`, already locked in) — approved explicitly before any code was written, per this file's own "ask first" rule.
- Also surfaced during this checkpoint's own audit of what actually gates `apps/brain`, not one of its deliverables: the lint/type-check CI gap — see the carried-forward debt list in `CLAUDE.md`.

### Real obligation typechecker

**Real obligation typechecker checkpoint (§21 Phase 4) — `apps/brain/src/obligo_brain/compiler/{typecheck.py,symbols.py}` written and proven against real Neon Postgres. No extraction pipeline, no LangGraph, no Z3 code exists yet — this checkpoint is symbol resolution and underspecification detection over an already-parsed AST only.**
- **The `parties` table (blueprint §8.2) didn't exist and was a hard blocker, not a design choice** — party-alias resolution (type rule 3) is this checkpoint's own named Phase 4 deliverable, and it had nothing to query against: checked every migration V1–V15 directly, confirmed absent. Not a Phase 5 pull-forward (Phase 5's own exclusion, per `packages/ir-spec/SPEC.md` section 11, is specifically the `obligations` table's lifecycle columns, not `parties`). Built as `apps/core/.../V16__create_parties.sql`, matching §8.2's inventory entry exactly (`id`; `org_id`; `canonical_name`; `aliases text[]`; `kind`; `external_ids jsonb`; `merged_into` self-FK; unique `(org_id, lower(canonical_name))`; GIN on `aliases`), RLS enabled and `FORCE`d identically to `organizations`/`sources`/`segments`, `obligo_brain` granted `SELECT` only (party creation/merge is a human-facing Phase 5 domain-layer concern, not this typechecker's). Applied to the real Neon branch via the Flyway CLI (the same recipe `ci-brain.yml` already uses) and verified directly against `information_schema`/`pg_class`, not assumed from the migration file: RLS on and forced, `obligo_brain`'s grant is `SELECT`-only, no grant added for `obligo_app` (no party-management endpoint exists yet to use it).
- **Tenant isolation is reused, not rebuilt.** `typecheck()` takes no `org_id` parameter; it relies on the caller having already called `TenantContext.set(org_id)` and opens its own `tenant_scope()` internally for the party-resolution query, the identical ambient-context convention every other apps/brain DB access already uses (`platform/tenancy/db.py`, `api/v1/sources.py`, `tasks/segmentation.py`). Deliberately not given an explicit `org_id` parameter instead, even though that would read as more obviously "pure" — introducing a second, different tenant-passing convention alongside the ambient one used everywhere else in this codebase was judged the worse inconsistency. Proven with the same real-Neon, skip-if-unset, owner-seeds/`obligo_brain`-reads discipline as `test_tenant_isolation.py`: a party registered in one org is invisible when typechecking under a different org's `TenantContext`, over RLS, not app-level filtering.
- **Of the six type rules, three fire for real, two never reach this function, and one is a permanent unconditional flag in v1:**
  - Rule 3 (party-alias resolution) is the one rule with real, data-backed resolution in this checkpoint — `symbols.resolve_party()` matches an alias against `parties.canonical_name`/`aliases` and returns a `ResolvedParty`, or leaves the alias `UnresolvedParty` (the AST's existing two-state `PartyRef` shape *is* the `UNRESOLVED_PARTY` signal; no separate sentinel was invented for it, per `packages/ir-spec/SPEC.md` section 4's own convention). An ambiguous multi-row alias match is treated as no match, not a guess.
  - Rules 2 (`BY`/`DURING` date resolution) and 4 (trigger resolution) fire consistently — an unresolved `DateRef`/`TriggerRef` always marks `underspecified` and records its dotted path in `missing_fields` — but always resolve to "stays unresolved" in this checkpoint, since neither has a real data source to resolve against yet. See the two carried-forward debt entries in `CLAUDE.md` for exactly what's missing for each and which future checkpoint owns building it — not restated here.
  - Rule 6 (business-day jurisdiction) isn't a resolution attempt at all, just an unconditional presence check: any `Duration` with `unit == "bd"` is flagged `underspecified` outright in v1, for the same missing-data reason covered by the debt entry in `CLAUDE.md`.
  - Rules 1 (`WITHIN` requires an explicit unit) and 5 (`ACTION` must be in the closed taxonomy) are **already fully enforced by the grammar** (`duration: NUMBER UNIT` makes the unit mandatory; `ACTION`'s own terminal alternation is the closed 34-verb taxonomy) — a `WITHIN` with no unit, or an action outside the taxonomy, fails to parse and never reaches `typecheck.py` at all. Confirmed by re-reading `grammar/obligation.lark`, not assumed from the type-rule list — these two rules have no corresponding logic in `typecheck.py` because there is nothing left for them to check by the time an AST exists.
- **One deliberate non-decision: `temporal is None` is never flagged**, even though `packages/ir-spec/examples/underspecified-missing-unit.json`'s own note assigned "how to recognize a vague temporal phrase as underspecified" to "the next checkpoint" — this one. Once "notify Customer promptly" has been through candidate extraction and DSL generation, the word "promptly" itself is gone; `temporal: None` in the parsed AST is genuinely indistinguishable from an obligation that correctly has no temporal element at all, using only the AST this function receives. Recovering that distinction needs the source text or the extraction candidate, neither of which `typecheck.py` has access to by design (it takes an AST, not a document) — deferred to the extraction/critic stage (blueprint §6.3 stage 6), documented as a reasoned deferral in `typecheck.py`'s own module docstring, not a silent gap.
- **`typecheck(obligation: ast.Obligation) -> ast.Obligation`** — no separate result/diagnostics wrapper. `packages/ir-spec/SPEC.md` section 4's own convention (any typechecker-resolved field already carries a two-state UNRESOLVED/RESOLVED shape) plus the AST's existing `underspecified`/`missing_fields` fields are sufficient to represent every outcome this checkpoint produces; a caller checks `isinstance(result.obligor, ast.UnresolvedParty)` for the `UNRESOLVED_PARTY` signal rather than reading a bolted-on sentinel. The review-queue *routing* this implies (blueprint §6.3 stage 4: "unresolved party → review queue") is left to whatever owns the `obligations` table and its UI (Phase 5's domain model), per `SPEC.md` section 11's own scope boundary — this function's job stops at producing a correctly-annotated IR.
- **Proven against real Neon Postgres throughout, no mocking** — `tests/compiler/test_symbols.py` (5 cases: canonical-name match, alias match, no-match, ambiguous-match, cross-org RLS isolation) and `tests/compiler/test_typecheck.py` (12 cases, one per rule-and-disposition above, obligations built via `parser.parse()` on real DSL strings rather than constructed AST literals). Full `apps/brain` suite re-run clean afterward: 96 passed, 5 skipped (pre-existing, unrelated — fork-safety and OCR platform skips), 0 failed.

### Extractor + Span Grounder

**Extractor + Span Grounder checkpoint (§21 Phase 4) — `apps/brain/src/obligo_brain/graphs/{extraction.py,state.py}`, `apps/brain/src/obligo_brain/models/providers/{base.py,groq.py}`, `apps/brain/src/obligo_brain/prompts/{registry.py,registry.yaml,extraction/v1.yaml}` written and proven against a real Groq model, real cassettes, and real Neon Postgres. No IR Compiler, no LangGraph, no Z3 code exists yet — this is the first LLM call this codebase ever makes, plus the deterministic gate that makes its output trustworthy.**
- **Groq adapter is module-level `httpx` functions, deliberately not the `groq` PyPI package** — Groq's REST API is OpenAI-compatible (`POST /openai/v1/chat/completions`), `httpx` is already a dependency, and CLAUDE.md's "ask first before adding a dependency" rule plus blueprint §13.1 rule 2 ("every model sits behind an adapter interface") are both better served by one thin adapter than a second, differently-shaped SDK Gemini's eventual adapter would need its own version of anyway. `ChatModel` is a `Protocol`, not an ABC — `groq.complete()` (a plain function, same style as `platform/storage/supabase.py`) satisfies it structurally, and any test double (lambda, cassette-backed stub) *is* a `ChatModel` with no fake class hierarchy required. `model_id` is passed in by the caller from the versioned prompt's `model_constraints`, never hardcoded in the adapter — the pin belongs in the prompt artifact (§13.8), and `list_models()` exists as a manual, by-hand verification step (confirmed live against Groq's model list before `llama-3.3-70b-versatile` was written into `extraction/v1.yaml`), not an automatic boot check that doesn't exist yet.
- **The prompt registry structurally prevents document text from reaching the system prompt — not by convention, by construction.** `registry.render()`'s system value is `prompt.system`, returned completely unmodified — never passed through `.format()` or any other substitution — so `segment_text` cannot reach it even by a future coding mistake in that function; only the user message is templated (`{nonce}`, `{segment_text}` via plain `str.format`, no jinja2 — CLAUDE.md's "ask first"/Standing Principle 5 both argue against a templating dependency for two placeholders). The user message wraps `segment_text` in a nonce-delimited fence (`<<<SEGMENT_{nonce}>>>` / `<<<END_SEGMENT_{nonce}>>>`) so a document can't forge its own closing delimiter and make its content look like it ends before it does; the system prompt declares fenced content data, never instruction (§17.5 defense-in-depth). The fence is defense-in-depth, not the actual control — the real control is that nothing downstream (grammar, typechecker, grounder) can mutate state without all three agreeing first. Prompts are versioned files (`prompts/extraction/v1.yaml` + `registry.yaml` mapping task→environment→version), never edited in place; `Prompt.prompt_hash` is a SHA-256 of the raw unrendered template (system + NUL + user_template), independent of `input_hash` (which is per-call, segment-specific) — the pair `(prompt_hash, model_id)` alone answers "did this call use the prompt version we think it did" (NFR-10, §13.5).
- **Span grounding (`ground_candidates()`) is the actual correctness gate — pure, no I/O — and gets the heaviest test suite of anything built in this checkpoint**, per blueprint §21's acceptance criterion (span-grounding rate exactly 100%, zero ungrounded obligations reach the database, by construction). Two tiers, deliberately not three: Tier A (EXACT, `segment.text.find`) then Tier B (NORMALIZED — NBSP/whitespace-run collapse, zero-width-character removal, smart-quote/dash folding, with an index map back to original offsets so the stored span is always `segment.text[char_start:char_end]`, never the model's string). **Tier C (Levenshtein-tolerant fuzzy matching, blueprint §6.3's "≤5% tolerance for OCR noise") was deliberately rejected, with a concrete adversarial case proving why**, not just argued abstractly: in a 200-character clause, "shall" → "shall not" is a ~2%-edit-distance mutation that inverts the obligation's meaning — comfortably under a 5% threshold, which disqualifies fuzzy tolerance on the single most important correctness control in this project by that example alone (`test_ground.py::test_modality_inverting_mutation_is_rejected_the_tier_c_argument_made_executable` makes this concrete, not hypothetical). The OCR-noise case Tier C exists for is already covered by `segments.ocr_confidence`/`LOW_OCR_CONFIDENCE` (Phase 3), which doesn't carry this hazard. An ambiguous multi-occurrence match (Tier A or B) is rejected outright (`AMBIGUOUS_SPAN`), never guessed between candidates — the same precedent `symbols.resolve_party()`'s ambiguous-match handling set.
- **`agent_runs` (blueprint §8.2's own inventory, never migrated — checked V1–V16 directly) was built now, at this checkpoint, not deferred again.** CLAUDE.md's debt list was already three entries deep in "called non-negotiable, never built" (Idempotency-Key/X-Request-Id, the cross-tenant leakage suite, `apps/brain`'s lint/type-check CI gate) before this checkpoint started — the first real LLM call this codebase makes was judged exactly the wrong moment to add a fourth. `input_hash` (`sha256(segment_id, prompt_hash, model_id)`) is recorded now even though the response cache that would key off it (§6.10) isn't built yet, specifically because backfilling it after these calls have already happened would be impossible. `cost_usd` is left nullable — computing it needs a real per-model pricing table, model-router scope, not this checkpoint's. RLS enabled and `FORCE`d identically to every other tenant-scoped table; `obligo_brain` granted `INSERT` only (nothing in this checkpoint reads `agent_runs` back — the eval harness and any future agent-run UI are separate, not-yet-built consumers), no grant to `obligo_app` (no endpoint reads/writes it yet).
- **Three-layer test strategy (blueprint §19.2), most of it never touching a network:** Layer 1 — pure unit tests with no I/O at all (`test_ground.py`, 20 cases including 2 hypothesis properties closing out `test_properties.py`'s deferred "grounding invariant"; `test_extract_candidates.py`, 5 cases, a fake `chat_model`, no live call). Layer 2 — cassette-replay (`test_extraction_cassette.py`, 5 cases, an `httpx.MockTransport` replaying a real previously-recorded Groq response — proves this code's handling of what the model actually said, not a guess at what it might say; each test skips individually if its cassette isn't recorded yet, rather than the whole file skipping as a block). Layer 3 — one deliberate, opt-in exception to "unit tests never hit a network": `test_extraction_live.py`, gated on `OBLIGO_LIVE_LLM=1` + `GROQ_API_KEY` (same skip-if-unset discipline as `DATABASE_URL`/`SUPABASE_*` elsewhere in this repo), not wired into CI — a rate-limited external dependency doesn't belong on the merge path, and catching model drift over time is the eval harness's job (§19.7), not built yet.
- **The cassette-mismatch finding: the real model was materially more robust than the 4 adversarial segments (each crafted to elicit one specific grounding-gate failure) assumed it would be — a real, live finding, not a shortfall in what got tested.** Recording session 2026-08-10, one live call per case against the real `llama-3.3-70b-versatile` extraction prompt, no retries: only `injection_canary` reproduced its intended category on the first try; `span_not_found`, `paraphrase`, and `malformed_json` did not, each producing a real-but-different outcome instead. **All three were kept and repurposed to prove something else real rather than discarded or silently re-recorded until they "worked"** — matching this file's own "a recorded finding is a false-positive signal with a prompt_version attached; throwing it away would make the extractor un-evaluable" reasoning (`graphs/state.py`'s `RejectionReason` docstring). Full per-cassette account (what each was recorded to elicit vs. what it actually proved, and exactly what's still genuinely unproven against real model output) lives in the carried-forward debt list in `CLAUDE.md` (the "No cassette demonstrates..." bullet) and `apps/brain/tests/cassettes/extraction/README.md` — not restated here.

### IR Compiler

**IR Compiler checkpoint (§21 Phase 4) — `apps/brain/src/obligo_brain/compiler/ir_compile.py` written and proven, no DB, no LLM, no network. This is the deterministic bridge between the Extractor/Span Grounder checkpoint's `GroundedCandidate` and the parser/typechecker checkpoint's `parser.parse()` — this checkpoint is DSL construction and classification only.**
- **`compile_candidate(candidate: GroundedCandidate) -> ast.Obligation | CompileFailure`**, plus a batch form `compile_candidates()` mirroring `ground_candidates()`'s partition shape (every input ends up in exactly one of the two output lists — nothing silently dropped). Pure function, same "do NOT use LangGraph when the flow is linear" reasoning already applied to the Extractor/Grounder — and deliberately NOT the parse-error repair loop (§6.3 stage 3's own, separate, not-yet-built failure path): no retry, no model call, classify-or-fail once.
- **Two real classification problems, both resolved by deterministic pattern matching, not a second LLM call** — Standing Principle 2 applies directly, since which of the five frozen `Temporal` forms an obligation gets, and what its extracted duration/date/trigger actually is, determines the compiled IR's meaning, not a draft:
  - `temporal_raw` → one of the five frozen `Temporal` forms, via five regexes each anchored to its own distinct leading keyword (`within`/`by`/`every`/`during`/`before`|`after`) — a closed-vocabulary problem structurally identical to what the grammar already does for `ACTION`/modality, not open-ended NLU. Because the five keywords are mutually exclusive leading tokens, no two forms can ever match the same phrase (`AMBIGUOUS_TEMPORAL` is structurally unreachable under this design and wasn't built as a separate reason).
  - `condition_raws` → each entry becomes exactly one `AtomPredicate` wrapping its raw text verbatim; multiple entries become multiple separate `IF "..."` clauses (implicit conjunction), never structured by detecting `AND`/`OR`/`NOT` inside a single string — unlike the temporal keyword vocabulary, boolean connectives in free legal text are genuinely ambiguous (`"not later than"` contains "not" but isn't a boolean negation), a real misclassification hazard a closed-vocabulary regex can't safely resolve. Because every string is trivially a valid atom, there's no failure mode here at all.
- **Unmappable `temporal_raw` rejects the whole candidate (`CompileFailureReason.UNMAPPABLE_TEMPORAL`), never silently compiles with `temporal=None`** — same "never silently drop" precedent as `NESTED_FIELD_NOT_IN_SPAN` discarding a whole candidate rather than patching one field. Dropping just the temporal field would silently understate the obligation (a timed "notify within 5 days" quietly becoming an untimed "notify" is a different, weaker obligation), and there's no AST slot to hold "has a temporal phrase, couldn't classify its shape" — `Temporal` is frozen at exactly five variants. A `GroundedCandidate` whose `temporal_raw` is genuinely `None` (no temporal phrase extracted at all) compiles `temporal=None` correctly — that's not a drop.
- **`modality`/`action`/`object_class` are only lightly, deterministically canonicalized** (case/whitespace normalization) and then left for the real grammar to validate as the closed-taxonomy authority — re-checking `ast.MODALITIES`/`ast.ACTIONS` here would duplicate what `grammar/obligation.lark`'s own terminals already enforce; any mismatch surfaces as `CompileFailureReason.PARSE_ERROR` with the parser's own precise diagnostic.
- **Ordering relative to `typecheck.py`: strictly before, never interleaved**, and this checkpoint changes nothing about tenant-scoped party-resolution timing. `compile_candidate()` opens no DB connection and calls `tenant_scope()` nowhere — pure, like `ground_candidates()`. Party aliases pass through unchanged as quoted strings; `parser.py` still turns them into `UnresolvedParty`; `typecheck.py`'s existing `tenant_scope()`-scoped `symbols.resolve_party()` call runs unchanged, strictly afterward.
- **A real, named scope limit: `DURING` only accepts two ISO-8601 date literals, not a defined-term alias on either side** (`"during the Term"` rejects, `UNMAPPABLE_TEMPORAL`) — splitting one free-text interval phrase into two separate alias termini deterministically is genuinely ambiguous, unlike `WITHIN`/`BY`'s single trailing phrase. Falls through loudly rather than guessing a split.
- **Real bug found and fixed by adversarial testing against realistic (non-textbook) phrasing, not caught by the original hypothesis/fixture suite:** `"by 2026-01-01."` — a trailing sentence-terminating period, exactly what a verbatim quote of the end of a real sentence looks like — silently downgraded a genuinely resolvable date into an unresolved alias (`UnresolvedDate(raw="2026-01-01.")` instead of `ResolvedDate("2026-01-01")`), a **silent corruption**, not a loud failure — the same category of bug this project's span-grounding discipline exists to catch, just one layer downstream of it. `EVERY`/`DURING` had the identical anchor problem, manifesting as safer-but-still-wrong under-rejection instead of corruption. **Fix scoped narrowly, not as a blanket period-strip:** trailing-period tolerance was added only at the three fixed-format token boundaries (`BY`'s date check, `EVERY`'s unit anchor, `DURING`'s second date anchor) — every one a closed, unambiguous format that can never legitimately contain a trailing period itself. Free-text trigger/alias capture (`WITHIN`'s/`RELATIVE`'s trigger, `BY`'s alias fallback) was deliberately left untouched and verified untouched (`"within 5d of Corp."` still preserves `"Corp."` verbatim in trigger text, not stripped) — an abbreviation's period is meaningful and must stay byte-verbatim, per this codebase's span-grounding discipline; only a token with zero legitimate use for a trailing period gets the tolerance.
- **The explicit lesson, not just the bug:** this checkpoint was first built and tested at `/effort medium`, using hypothesis-generated structural variation (units, amounts, arbitrary trigger text) plus hand-picked textbook phrasings ("within 5 business days of X") — and that suite passed clean while still shipping the silent-corruption bug above. A second adversarial pass, specifically testing realistic verbatim-quoted phrasing (trailing punctuation, non-canonical synonyms like "no later than"/"on or before"/"prior to", spelled-out numbers, "calendar days") found it immediately. **Regex/classification code whose input is real extracted document text — not just structurally-varied synthetic input — needs adversarial-phrasing testing as part of its first pass, not as a follow-up prompted by a direct question.** Same standing as the Extractor/Span Grounder checkpoint's real-cassette-over-synthetic-only discipline; apply it by default to any future deterministic classifier over LLM-extracted text (e.g. a future date/currency/jurisdiction normalizer), not only when asked.
- **Realistic phrasings confirmed correctly out of scope, not bugs** — `"no later than"`, `"not later than"`, `"on or before"`, `"prior to"`, spelled-out numbers (`"thirty (30) days"`), `"calendar days"`, and bare recurrence words (`"annually"`) all correctly reject as `UNMAPPABLE_TEMPORAL` rather than being silently misclassified, consistent with this checkpoint's own "strict over loose" decision — pinned as regression tests (`test_realistic_out_of_scope_phrasings_reject_rather_than_misclassify`) so the boundary stays a tested, intentional decision rather than an unexamined gap. Widening coverage to include these is real future scope for whoever next touches this classifier, not something to add quietly.
- **Proven with unit tests per temporal form/failure path plus two hypothesis round-trip properties** over the `WITHIN`/`EVERY` duration classifier across all 6 units (`tests/compiler/test_ir_compile.py`, 34 cases) — the classifier's own analog to `test_properties.py`'s round-trip property for the grammar itself. Full `apps/brain` suite re-run clean afterward: 140 passed, 39 skipped (pre-existing, unrelated), 0 failed.
- **Not built at this checkpoint, deferred, not silently skipped:** the parse-error repair loop (§6.3 stage 3's failure path — feeding the parser's message back to the LLM, ≤2 retries) and LangGraph itself (this function and Extractor/Grounder remain plain functions, not graph nodes, until the first real conditional edge exists — most likely the repair loop). Also still open from this checkpoint's original scope: a round-trip proof of `compile_candidate()` against `packages/ir-spec/examples/*.json`'s frozen fixtures, the way `parser.py`'s own checkpoint proved itself against those same fixtures — not built here, since those fixtures are already-typed IR (post-typecheck), not raw `temporal_raw`/`condition_raws` phrases, and reverse-engineering a plausible `GroundedCandidate` from each fixture's `ir` field to round-trip through was judged out of this checkpoint's scope, not attempted and quietly dropped. A real future task, not assumed done.

### Parse-error repair loop

**Parse-error repair loop checkpoint (§21 Phase 4) — `apps/brain/src/obligo_brain/graphs/repair.py`, `prompts/repair/v1.yaml`, `apps/core/.../V18__create_compile_quarantine.sql`. The first genuinely branching logic in the extraction pipeline. Still no LangGraph, deliberately — see below. No Z3, no Critic, no Linker.**
- **Budget resolved against the blueprint, not picked: `MAX_REPAIRS = 2`.** Full reasoning in the discrepancy note at the top of this section and in `repair.py`'s module docstring — five blueprint locations say 2, §21 alone says 3, and the blueprint's genuine "≤3" belongs to §13.8's separate, unbuilt schema-failure loop.
- **LangGraph deliberately NOT introduced, for the third time — with a falsifiable trigger written down so the next checkpoint doesn't re-argue it from scratch.** `state.py`/`extraction.py` had both pre-committed to "LangGraph gets introduced at whichever future checkpoint adds the first real conditional edge (most likely the parse-error repair loop)"; that prediction came due here and was declined on the merits. The cycle is one node with one back-edge and a bounded counter — a `while` loop expresses it completely. §6.8's own three justifications are either already satisfied (`agent_runs.node_trace` is the trace §6.8 says the graph maps 1:1 *to*; per-node retry is implemented here with domain-specific hint derivation a generic retry can't supply) or not yet needed (crash-resume: the whole loop is one synchronous call in one process). And Postgres checkpointing means a **second** dependency (`langgraph-checkpoint-postgres`) whose library-managed tables would hold org-scoped intermediate state — segment text, candidate JSON — outside this repo's RLS-from-creation discipline, which is a real security decision, not a packaging detail. **Trigger, in the same shape as the Kafka rule ("only if ≥3 independent event consumers actually exist"): adopt LangGraph when BOTH (a) ≥2 independent conditional edges exist — the Critic or Router node, not just this back-edge — AND (b) the pipeline spans more than one Celery task boundary.** "It's about time" is not a reason. Lives in `graphs/` rather than §6.1's suggested `compiler/repair.py` because it makes LLM calls and DB writes, and `compiler/` is deliberately I/O-free — a documented deviation.
- **Blueprint §6.3 stage 1 assumes "LLM → DSL"; this codebase does "LLM → JSON candidate" + deterministic DSL construction, so "feed the parser error back" needed translating rather than implementing literally.** Handing the model a Lark diagnostic about a string it never wrote would teach it to author DSL, routing around both the deterministic bridge and the grounding gate. Instead the parser's verdict is translated into field-level `RepairHint`s about the JSON the model did write. **That translation is exhaustive, not best-effort:** tracing every path from `_build_dsl` to the grammar (`_q()` is `json.dumps` so every `ESCAPED_STRING` slot is well-formed by construction; `segment_id` comes from the DB; offsets come from the grounder; `format_confidence`/`_format_amount`/`_unit_token`/`_DATE_RE` guard the rest), **exactly three fields can ever cause a `PARSE_ERROR`: `modality`, `action`, `object_class`.** All three are *classification* fields, none is span-grounded — which is precisely what makes repairing them safe. The raw Lark message is recorded in `agent_runs.node_trace` and never sent to the model.
- **No actionable hint ⇒ no model call.** An unexplainable `PARSE_ERROR` quarantines immediately with zero LLM calls; a repair prompt with no actionable hint is a coin flip that costs money and a rate-limit slot. Same "strict over loose" posture `ir_compile.py` takes on `DURING`.
- **A repair is structurally incapable of fabricating a quote.** The repaired candidate is built by copying the original `LLMCandidate` and overriding **only fields that carried a hint**; `span_text`, the aliases, `object_raw_text`, `condition_raws` and `confidence` are never read from the model's response at all. Standing Principle 2 applied to a retry: don't trust the model to obey an instruction that determines correctness — make disobeying it inert. The one repairable field that *is* grounded, `temporal_raw`, gets no bespoke check; the repaired candidate goes back through `ground_candidates()` in full, which stays the sole authority (a rewrite is caught as `NESTED_FIELD_NOT_IN_SPAN` and quarantined as `REPAIR_BROKE_GROUNDING`). A `null` `temporal_raw` is never accepted — that would "fix" the compile by silently turning a timed obligation into a weaker untimed one.
- **`UNMAPPABLE_TEMPORAL` is included but is honestly expected to be mostly unrepairable, and that is written into the code rather than discovered later.** `temporal_raw` must stay verbatim, so if the source says "no later than thirty (30) days after the Effective Date" *no substring will ever match* — the real fix for that class is widening `ir_compile._classify_temporal`'s vocabulary, already named as future scope there. The one genuinely repairable shape is **over-capture** (narrowing to a shorter verbatim substring that is a clean timing phrase). **Measure the real success rate when the eval harness (§19.7) exists; if it lands near zero, demote `UNMAPPABLE_TEMPORAL` to quarantine-immediately.** Worth noting the test fixture for this had to be chosen against the real classifier rather than assumed: the obvious-looking `"within 30 days of X, as extended"` actually compiles fine (WITHIN's trigger capture is `.+`) — the real over-capture case is `"every 30 days during the Term"`, since `_EVERY_RE` is end-anchored.
- **Batched by segment, not by candidate** — one call carries every currently-failing candidate with its own index and hints, the next carries only those still failing. `max_repairs=2` per *candidate* would cost up to 20 extra calls for a 10-candidate segment against a free tier that is rate-limited per minute and per day (§13.7/§13.8), and §6.10's budget-enforcing router isn't built. This bounds repair calls at 2 per segment regardless of candidate count and makes §3.9's "fail 3×" arithmetic exact. An attempt that changes nothing at all short-circuits the loop (`REPAIR_MADE_NO_PROGRESS`) rather than paying for a temperature-0 repeat of an identical payload.
- **`compile_quarantine` (V18) built now rather than deferred to Phase 5's review queue, because `agent_runs` genuinely cannot absorb this** — two independent hard reasons, both found by reading V17 directly: `obligo_brain` holds `INSERT` only (no `UPDATE`), so the repair stage physically cannot amend the extractor's row; and a `NO_ACTIONABLE_HINT` quarantine makes **zero** LLM calls while `agent_runs.model_id`/`prompt_id`/`prompt_version`/`prompt_hash`/`input_hash` are all `NOT NULL` — recording it there means fabricating values into the exact columns whose only purpose is reproducibility. Deliberately **not** the `quarantine` table §8.2 names, which §11.6/§12 define as poison-message/failed-upload storage with a 30-day purge — different lifecycle, different reader, different retention. RLS enabled and `FORCE`d from creation, `obligo_brain` `INSERT`-only, no `obligo_app` grant, no `UPDATE`/`DELETE` (a quarantine row is an immutable record of a decision; "this was later fixed" belongs to whatever supersedes it under a bumped `grammar_version`, per §6.2's recompile job).
- **`agent_runs` accounting: one row per LLM call, never aggregated.** Collapsing a multi-call sequence into one row loses per-call `model_id`/`prompt_version`, which breaks the moment §6.10's router does provider failover mid-sequence. `node='repair'` distinguishes them; cost/latency per segment is a `SUM` over the already-indexed `segment_id`, so no `parent_run_id` column was added — lineage travels via `node_trace` and via `compile_quarantine.agent_run_ids`. `cost_usd` still NULL (needs a pricing table; model-router scope).
- **`input_hash` had to diverge for repair, and the divergence is a real hazard avoided, not a style choice.** `extraction.py`'s `sha256(segment_id : prompt_hash : model_id)` would make two different failing candidates *from the same segment* collide on one `input_hash` — and V17 records that column as the key for §6.10's future content-hash response cache, so a collision would serve one candidate's repair for another's. `repair_input_hash()` hashes the rendered `system`/`user`/`model_id` instead. The general rule is "hash the actual rendered call inputs"; extraction's formula is a valid *special case* (segment_id + prompt_hash fully determine its rendered message). Documented in both places rather than left as two unexplained formulas.
- **The 34-verb taxonomy is hardcoded into `prompts/repair/v1.yaml`, not injected at render time** — an injected taxonomy would let the same `prompt_hash` produce different model behaviour whenever `ast.ACTIONS` changes, breaking exactly what `prompt_hash` exists to guarantee (NFR-10, §13.5). The cost is drift, bought back by `tests/prompts/test_repair_prompt.py` asserting the prompt's verb list equals `ast.ACTIONS` exactly, so a taxonomy change fails CI loudly and forces a version bump. Sidenote, deliberately not acted on: `extraction/v1.yaml` never lists the closed action set (only five examples), which is plausibly the dominant cause of repairable parse errors — whether listing all 34 helps or just biases the model toward a listed verb is an **eval-harness question**, not something to guess at here.
- **`registry.render_repair()` is a separate function rather than a generalized `render(prompt, **vars)`**: `render()`'s Standing-Principle-4 guarantee is a property of its *signature* as much as its body — a caller physically cannot pass anything but `segment_text`, so the set of things that could ever reach a system prompt is enumerable by reading one line. Widening to `**kwargs` would trade that for a convention. Both untrusted inputs (document text, and the failures payload which quotes document text) are nonce-fenced; asserted, not assumed, that a brace in the document cannot create a new substitution point (`str.format` only scans the template).
- **REAL BUG FOUND AND FIXED, in the Extractor checkpoint's code, not this one's: `INSERT ... RETURNING id` against a table granted `INSERT` only.** Postgres requires `SELECT` privilege on any column a `RETURNING` clause names, so `extraction.py`'s `_record_agent_run()` would have failed with `permission denied for table agent_runs` on **every** call against the real database. It survived because V17 had never been applied to the Neon branch *and* because no real-database test exercised `run_extraction` at all (both now separate debt entries in `CLAUDE.md`). Isolated live against the real DB before fixing — the identical statement without `RETURNING` gets past the privilege check and reaches the RLS policy — rather than inferred from the error message. Fixed by generating the surrogate key client-side in both callers, which keeps V17's minimal grant intact; widening it to `SELECT` to satisfy a convenience clause would trade a real privilege for nothing. **The generalizable lesson: a table whose grant is INSERT-only cannot use `RETURNING`, and only a real-database test can catch that** — the same standing as the IR-Compiler checkpoint's "adversarial-phrasing testing belongs in the first pass" lesson. Apply it to any future write path against a minimally-granted table.
- **Proven with 32 no-I/O tests** (`tests/graphs/test_repair.py` + `tests/prompts/test_repair_prompt.py` — 30 plain unit tests, 2 of them hypothesis properties: termination under any model behaviour, and totality — every input lands in exactly one output bucket) **and 6 real-Neon integration tests** (`tests/graphs/test_repair_db.py`) covering both tables' write paths, the `uuid[]` lineage round-trip, the zero-call quarantine path, RLS refusing a cross-org write on the write path, and the `run_extraction` regression above. 38 new tests total — and the arithmetic checks against the audit entry in `CLAUDE.md`: the IR-Compiler checkpoint's own real with-DB-env count was 173 passed, and 173 + 38 = **211**, the exact number the full re-run below reports. Full `apps/brain` suite re-run clean afterward **with `DATABASE_URL`/`BRAIN_DB_PASSWORD` set, so the real-database tiers actually ran rather than skipping**: 211 passed, 6 skipped, 0 failed — versus the 140 passed / 39 skipped the IR-Compiler checkpoint recorded without DB env, which is itself worth noting: **the previous checkpoint's "clean suite" was silently skipping 39 tests.** The 6 remaining skips were checked by name with `-rs`, not assumed from the typechecker checkpoint's older "fork-safety and OCR platform skips" description (which no longer matches — there is no OCR-specific skip anywhere in the current suite, and it undercounts what's actually skipping now): one `test_segment_source.py` case that specifically covers the *no-broker-configured* path and skips because this environment's `CELERY_BROKER_URL` **is** set; `test_extraction_live.py`'s live-LLM opt-in flag; one macOS fork-safety platform skip (`test_fork_safety.py`); and three `test_segmentation_task.py` cases that self-skip at runtime because they need a live Celery worker actually consuming tasks, not merely a configured broker URL. **This 211/6 count is this local machine's (macOS) number specifically, not a platform-independent one, and CI is expected to — and does — report a different total: checked against `ci-brain.yml`'s real run for this commit (`gh run view` on the workflow run this push triggered) rather than assumed to match, `ci-brain` reports 212 passed, 5 skipped, 0 failed.** The one-test delta is exactly the fork-safety skip: `test_fork_safety.py::test_without_the_mitigation_a_forked_child_inherits_the_parents_connection_fd` is itself platform-gated (its own skip reason says "Runs for real on Linux... where this class of fork hazard doesn't exist"), skips here on Apple Silicon, and ran for real and passed on CI's Linux runner — confirmed directly in the CI log, not inferred.
