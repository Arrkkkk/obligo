## What this project is

Obligo compiles natural-language obligations (from contracts, email, transcripts) into a typed, formally verifiable intermediate representation, detects contradictions between obligations using an SMT solver (Z3), and monitors each obligation against real-world evidence until it's fulfilled or breached.

The differentiator is the compiler (LLM candidate extraction → Lark grammar parse → semantic typecheck) and the verifier (Z3 lowering + unsat-core explanation). Everything else in the stack exists to support those two things. If a proposed change doesn't serve the compiler, the verifier, or making them demoable, treat it with suspicion.

## Local dev environment — DEVIATION FROM BLUEPRINT, READ THIS FIRST

**No Docker on the local machine**, by deliberate choice (not a temporary gap — don't try to "fix" this by installing Docker). This changes how Phase 1 and beyond are executed locally:

- **Postgres:** not run locally. Use a **Neon free-tier branch** (with the `pgvector` extension enabled) as the dev database. Connection string goes in `.env` (git-ignored), never committed.
- **Redis:** not run locally. Use **Upstash's free-tier Redis** (HTTPS/REST-based, no local process needed).
- **The three services run natively**, not in containers: Spring via `./gradlew bootRun`, FastAPI via `uvicorn` in a venv, Next.js via `npm run dev`.
- **Dockerfiles and `compose.yml` still get written** per the blueprint — they're needed for CI image builds (§20.4) and eventual deployment (§20.5) — but they are **not exercised locally** and are not a dependency for local development to work. Do not block any Phase 1 task on "the Compose stack running locally," because it won't be, by design.
- **`make dev` in this project means:** start Spring, start FastAPI, start Next.js natively, pointed at the cloud Postgres/Redis — not `docker compose up`. Write the Makefile target accordingly.
- Docker becomes actually relevant again around Phase 9 (deployment) or whenever CI needs to build and push real images — not before.

- **Scoped before any code was written, in a dedicated conversation, per this phase's own standing discipline** — the conflict-candidate set, the conflict condition itself, the candidate/solver boundary, and the deterministic-vs-LLM question for explanation were all proposed, reviewed, and corrected across several rounds before implementation started. Two real corrections landed during scoping, both worth keeping on record since they shaped the final lowering: (1) an early worked example used an interval-*intersection* framing for what makes two obligations conflict — caught as wrong before code existed, because a `MUST DELIVER` in January and a `MUST_NOT DELIVER` in June never intersect and are trivially satisfiable, while two obligations whose windows *do* intersect can still be either SAT (partial overlap) or UNSAT (full containment) depending on direction. (2) A confidentiality-vs-payment worked pair was walked through concretely to confirm the candidate-set filter's object-class clause actually excludes unrelated subject matter between the same two parties, not merely asserted to.
- **The conflict condition actually implemented is residual-emptiness, not intersection and not subset-in-either-direction as a standalone rule** — `docs/VERIFIER.md`'s own "The conflict condition" section has the full derivation. For the two-obligation case this reduces to a clean, testable statement: `MUST(W)`/`MUST_NOT(P)` is unsat iff `W ⊆ P`. Proven two ways: worked fixtures (`tests/verifier/test_verify.py`'s Example A — containment, UNSAT; Example A′ — partial overlap, SAT; Example S/T — prohibition nested inside a wider duty window, SAT because January and March survive outside the carved-out freeze; Example B — a genuine 3-way conflict where every pair is individually SAT and only the group together is UNSAT, the concrete justification for solving candidate sets rather than pairs) and a hypothesis property checking the real Z3 verdict against an independent, pure-Python set-containment oracle across hundreds of generated interval pairs (`test_must_must_not_unsat_iff_duty_window_is_subset_of_prohibition`).
- **Act keys are why two `MUST`s never conflict with each other regardless of their windows, by construction, not by a runtime check** — every MUST/SHOULD gets its own fresh Z3 `Int`; two duties to perform the same kind of act are two acts, not a shared performance. This is what keeps ordinary supersession (a later amendment's new deadline) from being read as a fabricated contradiction, and it's pinned as its own hypothesis property (`test_must_must_never_conflicts_regardless_of_windows`, and symmetrically for `MUST_NOT`/`MUST_NOT`) rather than left implicit in the worked examples alone.
- **The action-antagonism table (`RETAIN`→`DELETE`, `WITHHOLD`→`DISCLOSE`) closes the product's own headline example** ("a retention policy contradicted a deletion promise," this file's §1.3 vision) — `DELETE` and `RETAIN` are different actions in the closed 34-verb taxonomy, so a literal `MUST RETAIN`/`MUST DELETE` pair shares no act key and a plain modal check never fires on it without this table. Deliberately one-directional, not a symmetric pair, and that's a real semantic distinction, not an oversight: `RETAIN`/`WITHHOLD` describe a continuous state held throughout a window (the same shape as a `MUST_NOT`'s own forbidding window), `DELETE`/`DISCLOSE` describe a point-in-time act — "must delete by March 1" does not forbid retaining right up until the deletion, so the reverse direction is deliberately absent and pinned as its own regression test (`test_antagonism_is_not_symmetric_must_not_retain_does_not_imply_prohibition_on_delete`, `test_delete_must_never_implies_a_prohibition_on_retain`). Seeded strictly with exactly these two pairs, matching `ir_compile.py`'s own "strict over loose" posture — plausible-but-arguable pairs (`TERMINATE`/`MAINTAIN`) are deliberately left out.
- **Explanation is deterministic, template-based per finding kind, with zero LLM calls anywhere in the module — approved as proposed, without qualification, before implementation started.** Every fact in a rendered sentence is read directly from the minimal core's own labels (obligor name, action, object phrase, real dates); Standing Principle 2 and blueprint §6.7's own "the claim comes from the core... never let the model invent the reason" apply directly, and the span-grounding Tier-C precedent (`"shall"` → `"shall not"` inverting a clause's meaning at ~2% edit distance) is the concrete reason a polish step isn't added even as an option in this checkpoint.
- **Conditions lower to plain Z3 `Bool`s asserted as bare literals, not used to guard the modal/window facts** — a simplification found during implementation, not part of the original scoping proposal (which described `Implies`-guarded assertions): since condition literals are already assumed true per the approved design, guarding the window facts by them changes no verdict, only adds unused machinery. Same atom text across two different obligations' conditions is the same Z3 variable, which is what lets `IF "X"` in one obligation and `IF NOT "X"` in another genuinely contradict each other (`CONDITION_CONTRADICTION`, `tests/verifier/test_verify.py::test_condition_contradiction_without_any_modal_conflict`) — and, separately, what lets a `.cond` fact and a `.window`/`.prohibition` fact be found as two *independent* minimal cores in one solve when both are genuinely present (`test_condition_contradiction_isolated_no_temporal_overlap_at_all`, which real-world both contradicts on conditions and conflicts modally, and the multi-core enumeration correctly reports both).
- **Multiple independent conflicts in one candidate group are enumerated via Z3 assumptions, not `push`/`pop`** — another implementation-level refinement of the scoping proposal's conversational description. Every fact is asserted as `Implies(selector, constraint)`, with the selector passed as an *assumption* to `solver.check()` per call rather than permanently asserted true; this is what makes deletion-based minimization and multi-core search both possible by varying which selectors are active per call, reusing one `Solver` object throughout a group's search, bounded at 5 cores total and a 120s timeout (`Z3_TIMEOUT_MS`, matching blueprint §4.2's own constant) that surfaces as `VerificationResult.timed_out_groups`, never a silently-claimed SAT.
- **`TEMPORAL_IMPOSSIBILITY` (an obligation's own reversed `DURING` bounds) is detected in pure Python, not through Z3** — `intervals.is_empty()` on the obligation's own window, checked before candidate grouping even runs. Routing a self-contained defect through the solver would risk it being misattributed to whichever obligation it happened to be grouped with; detecting it separately also means a `TEMPORAL_IMPOSSIBILITY`-flagged obligation needs no candidate partner at all to be caught, unlike every other finding kind.

- **A precise, mechanical Tier-2 scoring rule was designed before any annotation started:** alignment by span-offset IoU (≥0.5) within one segment, then a conjunctive per-field predicate (modality, action, obligor, obligee, object_class, temporal incl. duration/unit exactness, conditions as an order-insensitive-but-count-sensitive set, underspecified, missing_fields excluded from the predicate but reported). Free-vocabulary fields (object_class, and — a real finding below — action) are scored against an annotator-authored accept-set fixed at gold-authoring time, deliberately replacing §6.11's judge-model proposal (no Gemini adapter exists in this codebase; Standing Principle 2 argues against a second model grading a field's correctness rather than a human-fixed accept-set doing it once).
- **10 synthetic segments were drafted and gold-annotated item by item, under explicit human sign-off per item** — not batch-approved. Real corrections made during that review, not silently accepted as first-drafted: an obligee direction rewritten from inferred to textually explicit ("for the benefit of Customer" added, so the party owed the duty is a real substring rather than a guess); a `DURING` item's accepted-outcome set made to explicitly include "fails as a known, named gap" rather than silently assuming resolution; a multi-condition item's scoring rule confirmed strict (exactly two separate `Condition` entries, not a count-agnostic accept-either) and confirmed as testing the extractor's own list-splitting behavior, not asking `ir_compile.py` to do the AND/OR-within-one-string detection it explicitly doesn't do.
- **Two real, unrelated pacing bugs were found and fixed in the pilot script (a throwaway harness, not production code) before any full run completed cleanly.** First: an unpaced sequence of live calls hit a real `429 Too Many Requests` from Groq at call 12 of an approved 30-call budget — the pilot script had no backoff at all, a real gap between what the design proposal specified (adaptive re-pacing against real rate-limit headers) and what the throwaway script actually implemented. Fixed with a flat inter-call interval, initially. Second, caught before being trusted rather than after failing again: that flat interval was itself shown unsafe by real token math — 13 calls in 37.9s of wall clock is a sustained-equivalent rate of ~25,700 tokens/min, 2.14× the account's real measured 12,000 TPM ceiling (read via one live header-only call: `x-ratelimit-limit-tokens: 12000`, `x-ratelimit-limit-requests: 1000` — both genuinely measured and both wrong relative to blueprint §13.3's stated ~6,000 TPM/~14,400 RPD figures, in opposite directions). The pilot's own clean run at that pace was evidence of unused burst/bucket capacity absorbing a short burst, not evidence the rate was sustainable. Replaced with a sliding-window token-rate limiter keyed on each call's own real returned token count (no header-parsing dependency, self-correcting against actual observed call sizes) before any further live call was made.
- **Also lost and recovered, same session:** the pilot script's first version scored and wrote results only after its entire 10-segment loop finished; the mid-run 429 above meant the whole run's results — including 8 already-successful segments — were discarded when the process crashed, because nothing had been persisted yet. Fixed by moving the score-and-write to run immediately after each segment's own `run_pipeline()` call, inside the loop, so a crash on segment N only costs segment N; segments 1..N-1's JSON files survive on disk regardless, untouched by the (unconditional, and still exception-safe) Neon cleanup in the script's `finally` block, which was verified — by rereading the actual code, not asserted from memory — to still fire correctly on any exception and never touch the result files at all.
- **Run twice, live, real Groq (`llama-3.3-70b-versatile`, temperature=0.0), real Neon (a fresh eval `org_id` + 2 registered parties, ingested and cleaned up per run), real `run_pipeline()` — no mocking anywhere in either run.** Both runs: 13 of 30/380 approved calls used, zero `429`s once the token-aware pacing was in place. **Run 1: 6/10 items scored `FULLY_CORRECT`-or-expected.** Failures: one `MISSED` (temporal trigger clause truncated by the model to `"within 5 days"`, dropping the mandatory `of <trigger>` tail `_WITHIN_RE` requires — `UNMAPPABLE_TEMPORAL`, one repair call made no progress, quarantined); one `UNEXPECTED` (see the clause-exclusion finding below); one `PARTIAL` (an `object_class` accept-set gap, model said `customer_personal_data`, gold's accept-set didn't include it); one more `MISSED` (same clause-exclusion pattern as the `UNEXPECTED` case). **Run 2 (fresh org, identical script, identical 10 sentences): 6/10 again, but a different six** — the first run's temporal-truncation `MISSED` item resolved cleanly this time; a different item that had compiled cleanly in run 1 came back `PARTIAL` this time on an `action` mismatch (model said `PROVIDE`, gold required `REPORT` — both are valid entries in the 34-verb taxonomy for the same real sentence); the other three non-clean items reproduced byte-for-byte identically, including the exact rejection-detail strings.
- **Real, load-bearing finding, confirmed by direct empirical reproduction, not a single run's noise: temperature=0.0 is not a determinism guarantee in practice.** Two live calls against the identical prompt, identical segment text, identical model, identical temperature produced different extractions for 2 of the 10 items. This has a direct design consequence for the real 100-item harness, not yet acted on: a single live run's fully-correct rate is a point estimate with real sampling noise even holding everything else fixed, so either gold items need to be run ≥2× in any regression-gating use of this harness, or every published number needs an explicit single-run caveat rather than being read as a fixed ground truth.
- **A second real finding, reproduced identically across both runs (not one-off): the extractor sometimes excludes a leading subordinate clause from `span_text` while still populating `temporal_raw`/`condition_raws` with content quoted from that excluded clause** — for sentences of the shape "During the period from X to Y, [main clause]." and "If A and if B, [main clause]." — caught correctly both times by `ground_candidates()`'s nested-field check as `NESTED_FIELD_NOT_IN_SPAN`, discarding the whole candidate before it ever reaches `ir_compile.py`. This is the grounding gate doing exactly its documented job (Standing Principle 4, CLAUDE.md's own "if a candidate's span text doesn't literally appear in the source segment, discard it" rule extended to nested fields) holding under live, unscripted model output for the first time — a positive result, not just two failures. But it is real and reproducible, not a fluke (identical `span_text`, identical rejection-detail string, both runs), and it is not universal — a third item with the identical leading-`If`-clause shape succeeded both times, so this is an intermittent, not deterministic, extraction-prompt behavior. **Worth its own investigation before real corpus annotation starts**, since real CUAD/EDGAR obligation sentences plausibly have this exact shape (a conditional or temporal clause fronting the main clause) more often than the synthetic pilot's small sample can characterize, and a systematic recall loss here would be invisible without a dedicated corpus slice or prompt-iteration checkpoint built to isolate it. One direct, secondary consequence: the specific pilot item built to probe whether `_DURING_RE`'s literal `".."`-joined date syntax is ever reachable from real model output never actually reached that check in either run, for this exact reason — that question is still genuinely untested, not answered by either run's `UNEXPECTED`/`MISSED` verdict.
- **A third real finding: the original scoring design's assumption that closed-taxonomy fields (`modality`, `action`) are safe for hard exact-match, reserving accept-sets for open-vocabulary fields (`object_class`) alone, is wrong.** Run 2's `action` mismatch (`PROVIDE` vs. gold's `REPORT`, both valid 34-verb-taxonomy entries for "submit a compliance report") shows a closed taxonomy doesn't guarantee a *unique* correct label for a given sentence — multiple taxonomy verbs can be equally defensible. The real 100-item gold set's scoring rule needs `action` accept-sets too, not just `object_class`, wherever a sentence's verb is genuinely polysemous under the 34-verb list.
- **No annotation-rigor claim is made beyond what was actually done.** All 10 items were reviewed and corrected individually, one at a time, with explicit sign-off per item (see the corrections bullet above) — this is not padded into a claim about the real 100-item set's eventual rigor, which hasn't started and needs its own decision, separately made, about process (repeated solo review vs. an independent second reviewer or held-out double-annotated sample) before it does.
- **Nothing here closes, or partially closes, either open Phase 4 acceptance criterion.** Criterion 1b (compile success ≥90% on the dev corpus) and criterion 2 (Tier-2 fully-correct-IR rate ≥80% on the gold set) remain **Unmeasured**, identically to how the ir_hash checkpoint's table above already listed them — this checkpoint sanity-checked the measuring instrument, not the thing it will eventually measure.

That confirmed `_locate_span()`/`_is_grounded_substring()` do no trimming of any kind; the narrowed `span_text` was already exactly what the model itself had emitted. Root cause is entirely LLM-extraction-side: the model was drawing `span_text`'s boundary at the main clause while independently quoting a fronting clause's content into `temporal_raw`/`condition_raws` — directly violating the v1 prompt's own already-stated "every nested field MUST be a literal substring of span_text" rule, not a rule the prompt was missing.

The grounding-invariant hypothesis property never touches nested fields at all (`temporal_raw`/`condition_raws` stay at their `None`/`[]` defaults throughout its strategy, which only varies `prefix`/`span`/`suffix` over a flat alphabet). - **Deliberately narrow, on explicit instruction — not the broader clause-boundary fix the investigation itself flagged as plausible.** `prompts/extraction/v2.yaml` only strengthens the rule for the confirmed failure shape: a subordinate clause fronting the main clause. ## Standing principles (do not violate these without asking)

1. **The system must be demoable at every commit.** Don't leave the stack in a broken state overnight.
2. **Deterministic core, probabilistic edge.** Anything a parser, typechecker, or solver can decide must not be decided by an LLM. If you're about to have a model output something that determines correctness (not just a draft/candidate), stop and ask.
3. **One trust boundary, three enforcement layers** for tenant isolation: gateway → application (`TenantConnectionPreparer` AOP setting the RLS GUC per-transaction + `@PreAuthorize`) → database (RLS, `FORCE`d, fail-closed). All three, always. Note: there is no JPA/Hibernate anywhere in `apps/core` — it's `JdbcTemplate` throughout, so "Hibernate `@Filter`" (as blueprint §10.9's diagram depicts for Layer 2) does not apply to this codebase; Layer 2 is the AOP described above, not a Hibernate filter.
4. **Every LLM output is untrusted input** — including, especially, when it originates from a document the user uploaded. Never concatenate document text into a system prompt.
5. **Prefer deleting a technology over adding one.** If a task seems to need a new piece of infrastructure, check the "explicitly deferred" list below first — it's probably already been considered and rejected for now.
6. **Property-based tests over code that touches real extracted or quoted document text must vary semantic/syntactic complexity, not just surface form, before their coverage counts as adequate.** Added after this exact blind spot cost real time twice, independently, in Phase 4: the IR-Compiler checkpoint's trailing-period bug (hypothesis-generated structural variation — units, amounts, arbitrary trigger text — plus hand-picked textbook phrasings, both passed clean while shipping a silent corruption on a realistic trailing sentence-period) and the leading-subordinate-clause grounding-fix checkpoint's bug (`test_ground.py`'s `NESTED_FIELD_NOT_IN_SPAN` cases and its grounding-invariant hypothesis property both vary only surface form — arbitrary alphabet strings, unrelated fabricated phrases — never real clause-structure complexity like a sentence-fronting subordinate clause). Before trusting a property/hypothesis suite's coverage for anything downstream of real extracted or quoted document text, ask explicitly: does this generator vary semantic/syntactic complexity, or only surface form? A generator that only varies the latter can pass exhaustively while missing an entire failure class — and, for anything whose "function under test" is actually an LLM's behavior rather than pure code (the grounding-fix case, not the IR-Compiler case), no property generator can close the gap at all; only sampling real model output (cassette or live) can.

## Non-negotiable engineering rules

- **Idempotency:** every mutating endpoint accepts `Idempotency-Key`. Every response carries `X-Request-Id`.
- **Tenant isolation:** every tenant-scoped table has `org_id` and an RLS policy from the moment it's created — not retrofitted later. Its repository must implement `TenantScopedRepository` (`apps/core/.../platform/tenancy/`), which `TenantIsolationArchitectureTest` enforces at build time: every public method must be `@Transactional`, and no raw `DataSource`/`Connection` field is allowed. This proves the precondition for isolation, not isolation itself — the actual guarantee is still the RLS policy + `TenantConnectionPreparer`, so write and test each new repository's isolation behavior for real, the ArchUnit rule alone isn't sufficient.
- **No `localStorage`/`sessionStorage` for tokens.** Access tokens live in JS memory only. Refresh tokens are `HttpOnly` cookies.
- **Migrations are immutable once merged.** Corrections are new migrations, never edits to old ones. Use expand/contract for anything destructive.
- **No raw SQL string concatenation, ever.** Parameterized queries only, in both Java and Python.
- **Extraction/compiler output must cite a verbatim source span.** If a candidate obligation's span text doesn't literally appear in the source segment, discard it — don't try to "fix" or reinterpret it.
- **Prompts are versioned files, not inline strings.** Once Phase 4 starts, every prompt lives in `brain/prompts/` with a version and is never edited in place — bump the version.
- **Every LLM call records `model_id`, `prompt_version`, cost, and latency.** Without this, nothing about the AI pipeline is reproducible or debuggable later.
