## What this project is

Obligo compiles natural-language obligations (from contracts, email, transcripts) into a typed, formally verifiable intermediate representation, detects contradictions between obligations using an SMT solver (Z3), and monitors each obligation against real-world evidence until it's fulfilled or breached.

The differentiator is the compiler (LLM candidate extraction → Lark grammar parse → semantic typecheck) and the verifier (Z3 lowering + unsat-core explanation). Everything else in the stack exists to support those two things. If a proposed change doesn't serve the compiler, the verifier, or making them demoable, treat it with suspicion.

## Local dev environment — DEVIATION FROM BLUEPRINT, READ THIS FIRST

**No Docker on the local machine**, by deliberate choice (not a temporary gap — don't try to "fix" this by installing Docker). This changes how Phase 1 and beyond are executed locally:

- **Postgres:** not run locally. Use a **Neon free-tier branch** (with the `pgvector` extension enabled) as the dev database. Connection string goes in `.env` (git-ignored), never committed.
- **Redis:** not run locally. Use **Upstash's free-tier Redis** (HTTPS/REST-based, no local process needed).
- **The three services run natively**, not in containers: Spring via `./gradlew bootRun`, FastAPI via `uvicorn` in a venv, Next.js via `npm run dev`.
- **Dockerfiles and `compose.yml` still get written** per the blueprint — they're needed for CI image builds (§20.4) and eventual deployment (§20.5) — but they are **not exercised locally** and are not a dependency for local development to work. Do not block any Phase 1 task on "the Compose stack running locally," because it won't be, by design.
- **`make dev` in this project means:** start Spring, start FastAPI, start Next.js natively, pointed at the cloud Postgres/Redis — not `docker compose up`. Write the Makefile target accordingly.
- Docker becomes actually relevant again around Phase 9 (deployment) or whenever CI needs to build and push real images — not before.

Phase 3 progress so far:
- Presigned upload flow (§11.2) — `sources` table (V10, RLS from creation, `SourceRepository implements TenantScopedRepository`), `POST /api/v1/sources/upload-intent`, `POST /api/v1/sources/{id}/commit`. `BlobStore` port + `SupabaseStorageBlobStore` adapter (§11.1's stated escape hatch to R2 later). Verified against real Neon + real Supabase Storage, no mocks — full upload → real PUT to the signed URL → commit → dedup-on-reupload flow, plus cross-tenant and capability-gating checks.
- File-security controls (§11.6) for this slice specifically: magic-byte MIME sniffing (`%PDF-` signature, via a ranged GET, not the client's declared Content-Type), a size cap, PDF-only rejection. `FileSecurityLimits`'s app-level cap/allow-list is checked against the Supabase bucket's own server-side config (`BucketConfigAgreementTest`, real API call) so the two independent layers can't silently drift apart.
- Real finding, not guessed from docs: Supabase's upload-sign endpoint does not honor a caller-supplied expiry — confirmed by passing `expiresIn` and decoding the returned token, which always carries a fixed ~2h lifetime. Blueprint §11.2 targets 5 min; nothing on our side can tighten a TTL Supabase itself fixes. Three follow-up properties verified live (not assumed) before deciding this was acceptable to document rather than something requiring an app-side mitigation: (1) `upsert:false` makes a second PUT to an already-uploaded key fail with `409 KeyAlreadyExists` and leaves the original content untouched — a leaked URL is dead the instant the legitimate upload lands, regardless of remaining token life; (2) the upload-signing token carries no read scope — the same token fails to `GET` the object it can write; (3) the token's signature is bound to its exact path — it fails with `InvalidSignature` against any other key. So the actual exposure isn't "a leaked URL is live for 2h" — it's narrower: a **pre-upload race on an abandoned intent** (client crashes, tab closes, upload never happens), for as long as that specific token stays valid. `SourceUploadService.commit` now caps that window at 30 min server-side (`MAX_PENDING_AGE`) — a `PENDING` source older than that is rejected with a typed `410 Gone` rather than falling through to storage verification, tested both ways (`commitRejectsAPendingSourceOlderThanTheStalenessThreshold`, `commitStillSucceedsForAPendingSourceUnderTheStalenessThreshold`). This shrinks the abandoned-intent race window to 30 min instead of Supabase's full 2h, but doesn't touch the live case: an attacker who wins the race within that 30 min window can still plant content that satisfies commit's own structural checks (size equality, magic-byte signature) — those checks validate shape, not provenance, and the visible failure this causes on the legitimate client's own PUT (also a `409 KeyAlreadyExists`, same mechanism) is a detection signal, not a prevention. **Final state: bounded, not solved.** No cross-tenant leakage, no standing access, no post-upload risk, and a materially narrower window than the raw 2h token — but a determined attacker who wins a sub-30-minute race on an abandoned intent can still get content past commit's checks. Acceptable for this phase; revisit if content provenance (e.g., a client-side signature Spring could verify) becomes a real requirement.
- `source_versions`/versioning (§11.3) is deliberately not built yet — `sources.storage_key` hardcodes `v1`, documented in V10's migration comment. This is the one item from the earlier deferred list still actually deferred; the rest (below) are now done.
- PDF structural checks (§11.6) beyond magic-byte sniffing, using Apache PDFBox 3.0.7 (`PdfStructuralValidator`) — confirmed Apache 2.0, zero known CVEs at this version per OSV.dev, and the only mature non-AGPL PDF-parsing library in the JVM ecosystem (iText's license ruled it out) before adding it as a dependency. Active-content rejection (embedded JavaScript, launch actions, embedded file attachments) is a flat scan of every indirect object in the file's xref table (`COSDocument.getXrefTable()`/`getObjectFromPool()`), not a walk of the high-level action tree — every action, wherever it's referenced from, ends up as an indirect object this scan sees, so it isn't fooled by an action dictionary missing the often-optional `/Type /Action` key. Decompression-bomb guard is one guard with three components (confirmed from blueprint's own wording, not two separate checks): page count ≤500 (blueprint's own number), a 200:1 decoded-bytes-to-file-size ratio cap plus an absolute 500 MB decoded-bytes ceiling — computed via bounded chunked reads that abort the instant either cap is crossed, so measuring the ratio never itself buffers a bomb to completion — and a 10 s hard timeout on the whole structural-check phase. Proven with PDFBox-generated fixtures, not hand-written ones: a `"%PDF-1.4\n..."` byte string passes magic-byte sniffing but isn't a real, structurally valid PDF PDFBox can parse, which broke the existing happy-path tests the instant structural validation was added — the fix was the test fixture, not the validator (`PdfTestFixtures`, generated via PDFBox itself). Real embedded-JS PDF, real high-ratio "bomb" PDF, and a real tampered-hash upload are all proven end to end against real Supabase Storage (`SourceUploadFlowTest`), plus a faster, more exhaustive pure-unit suite (`PdfStructuralValidatorTest`) covering the validator's own logic with no infrastructure needed.
- Server-side SHA-256 recomputation (§11.6) is a **deliberate deviation from, not an implementation of, blueprint's two-tier design** — blueprint splits this into synchronous verification under 20 MB and an async worker above that; this codebase recomputes synchronously for every file up to the full 50 MB cap instead, since no worker infrastructure exists yet and SHA-256 over 50 MB costs on the order of 100–300 ms in Java, trivial next to the download itself. Same honest-framing pattern as `TenantScopedRepository`'s precondition-not-guarantee note: said plainly so a future reader doesn't mistake "we hash everything synchronously now" for "we built the async tier and just haven't switched it on."
- **Accepted, unmitigated gap: PDF structural validation runs in-process, not sandboxed.** Blueprint §11.6 calls for PDF parsing to happen in an isolated worker with no network egress and a read-only filesystem; none of that exists yet, so `PdfStructuralValidator` runs Apache PDFBox directly against untrusted, potentially-malicious upload bytes inside the main Spring process. Its 10 s timeout is the only mitigation against a parser-level denial-of-service; there is no isolation at all against a parser-level memory-safety issue. Documented in its own bullet, not folded into a longer paragraph, because this is exactly the kind of thing a future security review needs to find in three seconds.
- `SourceUploadService.commit()` restructured from one `@Transactional` method into three phases (`SourceCommitGateway.gatekeep` → unlocked verification → `SourceCommitGateway.finalizeVerification`). **Performance-motivated:** once commit started downloading the full file and running PDFBox against it (up to the 10 s timeout) instead of just a HEAD and a 5-byte range GET, holding `findByIdForUpdate`'s row lock across that much external work risked exhausting this app's small Hikari pool (5 connections; 1 in tests) under concurrent large-file commits. Releasing the lock between phases reopens a race that the old single-transaction design closed for free — Postgres fully serialized concurrent `commit()` calls on the same source via the held lock, with no redundant work and no bug. That reopened race is a new failure mode this restructuring introduces, not a pre-existing bug it fixes; `finalizeVerification`'s `WHERE status = 'PENDING'` guard plus its zero-rows-affected reconciliation read is the new, deliberate mitigation for the window the restructuring itself opens.
- **Separate, correctness-critical finding — independent of the performance reasoning above, not a detail of it:** the three phases could not be implemented as private methods on `SourceUploadService` calling each other via `this.`. `@Transactional` is proxy-based AOP, and a proxy cannot intercept self-invocation — `this.gatekeep(...)` from inside the same class would have silently skipped the transaction entirely: no exception, `app.org_id` never set, RLS failing closed on every call (empty results, not a leak, but a completely broken feature that looks like a data problem, not a code problem). This is why `SourceCommitGateway` had to become a genuinely separate Spring bean — that requirement would hold even if the connection-pool concern above didn't exist at all. General rule worth remembering for this codebase, not just for this feature: the moment a method needing `@Transactional` is called via `this.` from within the same class, the annotation silently does nothing — the fix is always a separate bean, never a private method. Tenant isolation across all three phases was walked through explicitly as part of verifying this split, not assumed: org ownership is established exactly once (phase 1's `WHERE org_id = ?` + RLS), the unlocked middle phase runs zero SQL and operates only on an in-memory snapshot plus a storage key that already has `org_id` baked into its path, and phase 3 takes `orgId` as a plain threaded-through parameter, never re-derived. `TenantContext`'s Javadoc now carries a tripwire comment for this: the guarantee holds only because every step runs synchronously on one request thread, and breaks silently (not an exception — `TenantContext.get()` returns `null`, RLS fails closed) the moment anything in a flow like this crosses a thread pool boundary.
- **Regression caught and fixed, not a normal feature note:** `BlobStoreConfig`'s bean originally called `requireEnv("SUPABASE_URL")` unconditionally at bean-construction time, which Spring evaluates for every context load regardless of whether a given test touches storage. The first CI run after this slice landed proved it the hard way — 25 failures across unrelated test classes (`TenantIsolationTest` included), because the whole `ApplicationContext` failed to start the moment `SUPABASE_URL` was unset, before the CI secrets existed. This directly violated the pattern Phase 2 already established for exactly this situation (`GoogleOAuthClientRegistrationConfig`/`GoogleCredentialsPresentCondition` — no bean at all when credentials are absent, so the app boots fine and the feature activates once they exist) and Standing Principle 1 ("demoable at every commit"). Fixed the same way: `BlobStoreConfig`'s bean is now `@Conditional(SupabaseCredentialsPresentCondition.class)`, and `SourceUploadService` holds `ObjectProvider<BlobStore>` instead of a hard constructor dependency, throwing `BlobStoreUnavailableException` (→ `503`) only at the point an upload-intent or commit call actually needs storage. Proved both directions locally, matching how the Google-optional pattern was originally proved: full suite with `SUPABASE_*` entirely unset — app boots, all non-Supabase tests pass, `SourceUploadFlowTest`/`BucketConfigAgreementTest` skip cleanly (0 failures, 9 skipped); full suite with it set again — 0 skipped, all 127 tests pass. Worth remembering as a general rule, not just for this bean: any `@Bean` method that calls `requireEnv`/throws on missing config must be `@Conditional`, never called unconditionally, or it takes down every test in the module, not just its own.

**Real decision point, not just a dependency note: PyMuPDF is AGPL-3.0-or-commercial, not permissive.** Confirmed against PyPI/GitHub, not assumed — Artifex (MuPDF's maintainer) dual-licenses PyMuPDF under GNU AGPL v3 or a paid commercial license; there is no permissive option, and no mature alternative exists in the Python ecosystem with comparable layout/block extraction (`pdfplumber`/`pypdf` don't give the block-level structure the segmentation checkpoint needs — same "no alternative" reasoning blueprint §0.3 already gives). Explicitly accepted for now, on the same "checked and decided, not skipped" footing as the iText-vs-PDFBox call on the Java side. **What makes this different from that call:** PDFBox's Apache-2.0 license carries no obligation regardless of how apps/core is deployed; AGPL's network-copyleft clause is deployment-dependent — it triggers on *operating* the software as a network service for others, not on distribution. - **PyMuPDF text/layout extraction for born-digital PDFs (§11, §21)** — the first checkpoint that actually produces real segments, superseding V12's placeholder columns.   - `V13__segments_layout_columns.sql` adds `ordinal` (0-indexed, document-wide extraction order) and `page` (1-indexed, converted from PyMuPDF's own 0-indexed `page.number`) as `NOT NULL` columns, adds `UNIQUE (source_id, ordinal)` per blueprint's own segments row, and tightens `char_end`'s CHECK from `>=` to `>` (empty segments are filtered at extraction, not persisted). `layout jsonb` (bbox), `ocr_confidence`, `ts_start/end_ms`, `speaker` are all still deliberately not added — no consumer needs them until the page-rendering/highlighting, OCR, and ASR checkpoints respectively; blueprint's full segments row names all of them, this migration intentionally implements a subset.
  - **Real mistake caught before it shipped, not guessed correctly the first time:** the migration's first version assumed Postgres would name V12's `char_end >= char_start` CHECK constraint `segments_char_end_check` (column-level naming convention). Running it against the real Neon branch failed with `constraint "segments_char_end_check" of relation "segments" does not exist` — because that CHECK references two columns, Postgres classified it as a table-level constraint and named it `segments_check` instead. Confirmed the actual name via `pg_constraint` rather than guessing again, fixed, re-ran clean. Flyway's transactional DDL meant the failed first attempt left zero partial state (no added columns, no `flyway_schema_history` row) — verified, not assumed.
  - **Offsets are derived by construction, not by post-hoc comparison** (`apps/brain/src/obligo_brain/ingestion/loaders/pdf.py`) — the naive approach (extract full page text one way, extract blocks another way, `str.find()` each block into the full text) is a trap: the two PyMuPDF extraction modes aren't guaranteed to concatenate identically, and `str.find()` silently returns the *first* match, so a repeated phrase (a defined term, a table header) can get a silently wrong offset. Instead, `page.get_text("blocks", sort=True)` is called once per page, and each non-empty block is appended to a running per-page string with `char_start`/`char_end` read directly off that string's length before/after the append — the persisted text *is* what produced the offsets, so `page_text[char_start:char_end] == text` holds by construction. `ordinal` is a single counter incremented across the whole document (not reset per page), matching the `UNIQUE (source_id, ordinal)` constraint.
  - **Named limitation, demonstrated with real evidence, not left hypothetical:** round-trip correctness (offsets point at the right text) is guaranteed by construction; reading-order correctness (segments appear in visually sensible order) is not, for genuinely multi-column layouts — PyMuPDF's block ordering (`sort=True` included) is position-heuristic, not a true column-aware reading-order solver. Caught a real instance on the two-column BERT paper fixture: section heading "2.2" is extracted *before* "2.1"'s own body paragraph, because the two side-by-side columns get interleaved by y-coordinate. Asserted explicitly in `test_two_column_fixture_has_exact_offsets_despite_reading_order_caveat` so a future PyMuPDF upgrade or reordering fix changes that test loudly, not silently — and the same test proves the offsets stay exact regardless of the ordering being visibly wrong.
  - `POST /api/v1/sources/{source_id}/segment` (`apps/brain/src/obligo_brain/api/v1/sources.py`): reads the source row and persists segments through `tenant_scope()`, fetches bytes via a new minimal `SupabaseObjectReader`-equivalent (`platform/storage/supabase.py`'s `fetch_object` — deliberately not a full `BlobStore` port, since apps/brain only ever reads, never writes, storage). Re-segmenting an already-segmented source fails loudly with a typed `409` (via the `UNIQUE (source_id, ordinal)` constraint) rather than silently duplicating or silently no-op'ing — not idempotency, since nothing re-verifies prior results, but a safe, non-silent failure mode consistent with reprocessing/supersession semantics still being undecided (the same open question V12's own migration comment already named).

- **The most important design point in this checkpoint, stated in three places on purpose (this file, `V14`'s migration comment, `segments.ocr_confidence`'s own column comment, and `ocr.py`'s module docstring — four, actually) so it can't be missed by reading only one of them:** the Phase 3 acceptance criterion "segment offsets round-trip exactly to the source text" means two different things depending on which extraction path produced a row. PyMuPDF text-layer segments (`ocr_confidence IS NULL`) are exact against the PDF's own embedded text layer — ground truth, by construction, because PyMuPDF reads bytes the PDF itself declares as text. OCR segments (`ocr_confidence IS NOT NULL`) are exact against **Tesseract's own recognition output**, not against the physical page — the identical running-string offset-construction mechanism as the PyMuPDF path (`char_start`/`char_end` read off a running per-page string's length before/after each block append, so `page_text[char_start:char_end] == text` holds by construction either way) but a misread word is still round-trip exact — it's just exact to the wrong text. Do not read "round-trips exactly" on a scanned-page segment as "matches the source document"; it means "matches what Tesseract said the source document says."
- **Scanned-page detection is per-page, not per-document** (`obligo_brain/ingestion/loaders/pdf.py`) — a real requirement, not a hypothetical one: blueprint's own acceptance criteria name "mixed" documents as a case this phase must cover, and a per-document decision structurally cannot handle a PDF with some born-digital and some scanned pages. For each page, `page.get_text("text")` is measured for length only (never a source of offsets, so this doesn't reopen the str.find()-trap `pdf.py`'s own module docstring warns about) against blueprint's own stated threshold (>100 chars/page = born-digital); at or under, the page routes to `ocr.extract_ocr_page_segments` instead of block extraction. `extract_segments`'s per-page loop now dispatches to either path per page and threads a single document-wide `ordinal` counter through both, so a mixed document's segments still satisfy `UNIQUE (source_id, ordinal)` with no special-casing.
- **OCR extraction** (`obligo_brain/ingestion/loaders/ocr.py`) — rasterizes via PyMuPDF's own `get_pixmap(dpi=300)` (blueprint's own DPI number) rather than adding a second rasterization dependency (`pdf2image`/poppler); feeds the result to `pytesseract.image_to_data` (not `image_to_string`, which would discard the per-word confidence and bounding-box data the confidence check needs) and groups word-level results by Tesseract's own `block_num` — the closest analog to PyMuPDF's per-block granularity — joining words with a single space and reading `char_start`/`char_end` off the same running-per-page-string mechanism `pdf.py` already uses. Block order is Tesseract's own array order, a position heuristic like PyMuPDF's `sort=True`, not a true reading-order solver — the same named, not-fully-solved limitation as the existing two-column caveat, now true of this path too. `ExtractedSegment` was moved out of `pdf.py` into a new shared `segment.py` specifically to avoid a circular import (`pdf.py` calls into `ocr.py` for the per-page dispatch; `ocr.py` needs the same segment shape) — a structural necessity, not a style preference.
- **Confidence aggregation is MIN across a block's words, not mean — a deliberate, explicitly-reasoned choice, not the obvious default.** Averaging would let one badly-misread word (a date, a party name, a dollar figure — exactly the tokens a contradiction-detecting system cares about) get diluted into a passing score by a few high-confidence words around it; a single wrong word in a defined term is a real correctness failure for this project's whole thesis, not noise to be smoothed over. `ocr.is_low_confidence()` is the flagging primitive blueprint's decision tree calls for ("pages below threshold flagged `LOW_OCR_CONFIDENCE`... excluded from binding extraction, surfaced to the user, not silently used") — `LOW_OCR_CONFIDENCE_THRESHOLD = 60.0` is a documented judgment call (Tesseract's own scale is 0-100 with no universally validated cutoff), not a persisted boolean column or an actual exclusion-from-extraction step, since nothing does "binding extraction" yet (that's Phase 4's compiler) — this phase builds the flagging primitive a future consumer calls, not a premature enforcement point.
- **`V14__segments_ocr_confidence.sql`** adds the nullable `ocr_confidence REAL` column V13's own comment deferred ("meaningless for born-digital text, arrives with the OCR checkpoint") plus a `CHECK (ocr_confidence IS NULL OR (0-100))` and a `COMMENT ON COLUMN` carrying the full round-trip-exactness distinction above — deliberately in the column comment itself, not just in this file, so a future reader querying the table directly still sees it. NULL-ness of the column is the signal for which extraction path produced a row; no separate `source` enum column was added, since NULL vs. non-NULL already carries that without redundancy. Applied to and verified against the real dev Neon branch directly (column type/nullability, the CHECK constraint's actual definition, and the comment text all confirmed via `psycopg` against `information_schema`/`pg_constraint`/`col_description`), not just assumed correct from the SQL file.

Deliberately *not* sourced from an external host like archive.org: many of archive.org's own "PDF" downloads already carry a hidden OCR text layer baked in by their own ABBYY pipeline, which would silently defeat this checkpoint's own scanned-page detector (the page would report plenty of extractable text and never route to OCR at all) in a way that wouldn't be obvious from the file itself — a real, considered risk, not a hypothetical one, and the reason all three new fixtures are derived from PDFs already in this repo instead. `scanned_irs_1040.pdf` — the real IRS-1040 form content (same document as the existing born-digital fixture), rasterized at 300 DPI and re-embedded image-only, zero embedded text layer, confirmed via `page.get_text()` before trusting it as a fixture. `scanned_low_quality.pdf` — the same content, degraded (downscale/upscale blur, Gaussian blur, reduced contrast, blended noise) — tuned by actually running Tesseract against candidates, not guessed once: the first attempt (heavier degradation) came back as pure unrecognizable noise, 0 legible words, which would have proven nothing about confidence *flagging* specifically; the tuned version reads like a genuinely bad fax (16 segments, confidence 0-95, 11/16 below the 60.0 threshold, at least one segment still correctly recognized at high confidence) — real Tesseract output, not a fabricated confidence value. `mixed_born_digital_and_scanned.pdf` — page 1 a lossless `insert_pdf` copy of `public_domain_chart.pdf`'s real page 1 (genuine text layer, nothing re-rasterized), page 2 the same rasterized IRS-form content — the fixture that actually exercises per-page (not per-document) routing, confirmed by extraction: page 1 segments all `ocr_confidence IS NULL`, page 2 segments all not-NULL, from one `extract_segments` call. **Async-segmentation checkpoint (§21 Phase 3) — segmentation moves from a synchronous FastAPI request to a Celery task.** OCR is genuinely slow (the degraded fixture above took real, multi-second Tesseract passes); this checkpoint makes `POST /api/v1/sources/{source_id}/segment` background the work instead of blocking the request thread for it.

- **Contract change, not an addition:** POST no longer computes or returns segments. It validates the source, INSERTs a `segmentation_jobs` row (`V15`, below), enqueues `segment_source_task`, and returns **202** `{source_id, status}` — never `segment_count`, since that isn't known yet. A new **GET** on the same path returns job status (`QUEUED`/`PROCESSING`/`SUCCEEDED`/`FAILED`, `attempt_count`, `segment_count`, `last_error`). Three real design calls made explicitly, not assumed: (1) job state lives in a **new, separate `segmentation_jobs` table**, not an expanded `sources.status` — `sources.status` (`PENDING/UPLOADED/REJECTED/CORRUPT`, a Java-owned enum + CHECK, `V10`) represents the *upload* lifecycle; conflating it with the *segmentation* lifecycle would mean every future segmentation-state addition requires touching apps/core's Java enum for a concern apps/brain owns end to end. Matches blueprint's own already-quoted design intent ("durability handled via Postgres job-state reconciliation, not a second broker"). (2) apps/core learns status via a **new brain-side HTTP endpoint**, not a DB grant — preserves the existing boundary where apps/core has zero grants on any brain-owned table (`V12`'s own comment). (3) **Every source goes through Celery uniformly** — no sync/async split by "does this source need OCR," since determining that requires fetching and opening the PDF first anyway, which is most of the expensive part.
- **Tenant isolation through a Celery task, not an HTTP request — proven with the same rigor as the original contextvars design, not assumed to carry over.** `contextvars.ContextVar` does not cross a process boundary; a worker executing a task is a separate OS process from the request that enqueued it. `segment_source_task` calls `TenantContext.set(org_id)` explicitly from its own argument, `try/finally`-cleared, exactly what the endpoint used to do, just relocated. **What genuinely changed, stated plainly rather than glossed over as "no different":** `org_id` now also travels as a plain, serialized argument in a message on the Redis broker, not just an HTTP body — anyone holding the Redis broker credentials can now assert an arbitrary `org_id`, not just whoever can reach the endpoint with `BRAIN_SERVICE_TOKEN`, and a single unverified claim can now be replayed across a task's full retry lifecycle. Same underlying trust gap the shared-secret-gate debt note already names, genuinely widened, not a new problem in kind. Proven for real (`tests/tasks/test_segmentation_task.py`, real Neon + real Supabase Storage, no mocks): a different org's `TenantContext` sees zero rows for a task-written source's segments/job, and no context at all sees zero rows too (fail-closed) — RLS enforces isolation identically regardless of which entrypoint performed the write.
- **A real, code-level fork-safety hazard, found and fixed as part of this checkpoint, not deferred as a follow-up.** `get_engine()` (`db.py`) is a lazy, module-level singleton. Celery's `prefork` pool forks worker processes from a parent; psycopg connections are not fork-safe, so if anything called `get_engine()` before the fork, every forked child would inherit the parent's already-open sockets — tenant-isolation-adjacent, not just a stability concern, since `tenant_scope()`'s guarantee rests on "one connection = one transaction = one `SET LOCAL app.org_id`" holding for every checkout. Fixed via `db.reset_engine_for_forked_process()`, wired to Celery's `worker_process_init` signal (`tasks/celery_app.py`) — drops the stale singleton so each forked child builds a fresh `Engine` from scratch. **Proven against a real `os.fork()` and a real Neon connection** (`tests/platform/tenancy/test_fork_safety.py`), not asserted to exist: one test reproduces the bug directly (a child that doesn't call the reset inherits the parent's exact connection file descriptor, confirmed via `psycopg`'s own `fileno()`, not object-identity guessing across a process boundary) and a second confirms the reset is safe to call unconditionally.
- **A second, deeper finding made while building that proof, not assumed away — this one changed real operational guidance, not just test code.** The first version of the "does a reset child get a working new connection" test forked a parent that had *never* touched the database (the fully-disciplined case) and expected success. The child **segfaulted** instead — confirmed via `process.exitcode == -SIGSEGV`, traceback rooted in `socket.getaddrinfo()` inside psycopg's hostname resolution. Root-caused, not guessed: this is CPython's well-documented macOS fork-safety limitation (Apple's system frameworks, here the DNS resolver, don't survive `fork()` — the same reason CPython switched `multiprocessing`'s *default* start method away from fork on macOS since 3.8), independent of OpenSSL, independent of whether the parent touched Postgres at all. **Consequence, acted on, not just noted:** local dev on this Mac runs the Celery worker with **`--pool=solo`**, never `--pool=prefork` (`Makefile`'s `make dev` target, `tasks/celery_app.py`'s own docstring) — `--pool=prefork` is what CI (`ubuntu-latest`) and the real x86 Linux Hetzner prod target use, where this class of fork hazard doesn't exist. The specific test that would prove `prefork` safety is written to skip on darwin (with this exact finding as its skip reason) and assert real success on Linux — meaning it's expected to actually execute and pass in `ci-brain.yml`, not just always skip.
- **Minimal Celery + Redis wiring, deliberately narrower than blueprint's full `scan`/`parse`/`ocr` three-stage pipeline.** One task (`segment_source_task`), one queue (`ocr`, reusing blueprint's own §14 name since OCR latency is the actual reason this needs to be async at all). **Broker only, no result backend** — `task_ignore_result=True`; nothing calls `.get()`/`AsyncResult` since job state lives in Postgres (`segmentation_jobs`), avoiding a second, less tenant-scoped source of truth and avoiding spending part of Upstash's free-tier monthly command budget on redundant result storage. **`celery[redis]>=5.5`** specifically (not just "latest") — checked live, not assumed: kombu's Redis-broker disconnect-stability issues were fixed in kombu 5.5.0, shipped with Celery 5.5.0; this repo resolved to Celery 5.6.3/kombu 5.6.2/redis-py 6.4.0, within kombu 5.6's own documented `redis<6.5` constraint.
- **`acks_late=True` is the single most load-bearing setting, and the reason "not silently losing a source stuck mid-segmentation" is actually true, not just asserted.** Without it, Celery acks (discards) a task message *before* executing it — a hard-killed worker (OOM, exactly the risk blueprint names Tesseract/PaddleOCR as capable of causing) loses the task permanently and silently, no retry. With it, an un-acked message is redeliverable to another worker. **Two genuinely different failure classes handled by two genuinely different mechanisms, not one:** (1) catchable in-Python failures (bad PDF, transient Supabase fetch error) are retried via `self.retry()` with manual exponential backoff+jitter (blueprint's own §14 numbers — 300s/600s soft/hard limits, 3 retries — as the starting anchor, not yet revised against Tesseract's actually-observed latency since nothing has approached these caps), terminal failure writes `FAILED` to `segmentation_jobs` only on the last attempt (a retrying-but-not-yet-failed attempt deliberately does NOT flip status to `FAILED` — that would misrepresent a transient, still-retrying state as terminal; it records `last_error`/`attempt_count` while leaving status at `PROCESSING`). (2) the worker process dying outright (SIGKILL/OOM, or Celery's own hard `time_limit` SIGKILLing the worker) never runs any Python exception handler at all — `acks_late` redelivery is a broker-level mechanism, **not** the same as `self.retry()`, and does **not** increment `self.request.retries`; a task stuck in this failure class could in principle be redelivered indefinitely without ever tripping `max_retries`. This is exactly why a **staleness-reconciliation check** exists as a second, independent mitigation layer on the GET status endpoint (`STALE_PROCESSING_AFTER = 900s`, actively flips a stuck `PROCESSING` job to `FAILED` on read, same "fix it, don't just describe it" precedent as `SourceUploadService.MAX_PENDING_AGE`) — a periodic Celery beat sweep is the more robust version and is real future work, not built here, same "bounded, not solved" posture as this codebase's other interim mitigations. **Proven for real** (`tests/tasks/test_segmentation_task.py::test_task_exhausts_retries_and_marks_failed_on_a_real_missing_object`): a source whose `storage_key` points at an object deliberately never uploaded (a genuine Supabase 404, not a mock) drives the full retry arc — `attempt_count` reaches `MAX_RETRIES + 1`, terminal `FAILED` with a real error message — via Celery's own `.apply()` (which, verified interactively before relying on it, runs a task's real retry control flow fully in-process with zero broker involvement, the standard, documented way to test Celery retry logic without live infrastructure).
- **Upstash's actual max-concurrent-connections ceiling for the free tier is unverified, not silently assumed safe.** Checked their docs and troubleshooting pages directly (not inferred): a real `"ERR max concurrent connections exceeded"` error exists, but the tier-specific numeric limit isn't published anywhere found — their own docs point to `support@upstash.com` for it. `worker_concurrency` defaults to **2**, matching blueprint's own §14 OCR-queue number, as the deliberately conservative fallback rather than a guessed "safe" number — same "bounded, not solved" honesty as everything else here. Revisit once the real ceiling is confirmed.
- **Broker credential gap: closed out, and closing it surfaced two more real findings that changed the actual `celery_app.py` config, not just test code.** `.env` now has `CELERY_BROKER_URL` (the separate TCP+TLS `rediss://` connection string, distinct from `UPSTASH_REDIS_REST_URL`/`TOKEN`), and `secrets.CELERY_BROKER_URL` exists as a GitHub repo secret. `tests/tasks/test_celery_broker_integration.py` was run for real against live Upstash — twice, to confirm it's reliable and not a fluke — and passes both times.
  - **Finding 1: kombu's Redis transport defaults `visibility_timeout` to 3600s (1 hour)**, confirmed by reading `kombu/transport/redis.py` directly, not assumed from docs. Left there, `acks_late`'s whole purpose would have been defeated in real deployment — a worker OOM-killed mid-OCR wouldn't have its task redelivered for up to an hour. Fixed: `DEFAULT_VISIBILITY_TIMEOUT_SECONDS = 1200` in `celery_app.py`, deliberately well above `segmentation.HARD_TIME_LIMIT_SECONDS` (600s) — not just "shorter than the default," specifically sized to avoid a *different* hazard: a visibility_timeout shorter than a task's legitimate max runtime risks a second worker prematurely starting the same task while the first is still validly running, racing to write `segmentation_jobs` (the second worker's eventual failure could clobber a job the first already marked `SUCCEEDED`). `_mark_job_failed` also guards against this defensively now (`WHERE ... AND status != 'SUCCEEDED'`), a second, independent layer against the same race.
  - **Finding 2: even with a short visibility_timeout, automatic redelivery to an idle worker is NOT reliably prompt** — verified directly (a real worker left running 60+ real seconds after another was SIGKILLed never redelivered the message on its own), not inferred. kombu's restore-overdue-messages check only runs as a side effect of a consumer's own event-loop ticking; an idle worker on an empty queue may not tick often enough to notice.
  - **Finding 3: the "obvious" fix for Finding 2 — shortening `broker_transport_options['polling_interval']` so an idle worker ticks more often — was tried, and made things worse, not better.** kombu's `restore_visible()` uses an optimistic Redis `WATCH`/`MULTI`/`EXEC` transaction that silently no-ops (no exception, no `MutexHeld`) if it races a *concurrent* restore attempt — with the worker polling more often, an external reconciler's restore call now regularly lost that race. Confirmed directly: `zrevrangebyscore` correctly found the overdue entry every time; `restore_visible()` returned without error every time; the entry stayed un-restored across 5 retried attempts while a worker polled concurrently. The `polling_interval` change was reverted once this was understood. **The fix that actually works, confirmed directly:** perform the restore before any worker capable of racing it is even running — called in isolation, `restore_visible()` moves an overdue entry back to the queue reliably, every time.
  - **This is exactly why the Postgres-based staleness-reconciliation check (`STALE_PROCESSING_AFTER`, GET status endpoint) is the real, load-bearing safety net for "not silently losing a source stuck mid-segmentation" — not `acks_late`'s redelivery speed.** Directly validates blueprint's own already-quoted design philosophy ("durability handled via Postgres job-state reconciliation, not a second broker") — Redis's redelivery is real and correct when performed cleanly, but was never meant to be the sole or fast mechanism, and Findings 2–3 show real, verified rough edges under concurrent access that Postgres reconciliation doesn't have. A periodic Celery Beat task that calls `restore_visible()` itself (rather than relying on worker idle-polling) would be valid future hardening — this checkpoint's own isolated-restore test is effectively a proof-of-concept for exactly what such a task would do — but building it is real future work, not done here.
  - **Real test-authoring bugs caught and fixed along the way, not just infra findings** — worth naming since they're the kind of mistake worth remembering for next time: (a) `CELERY_VISIBILITY_TIMEOUT_SECONDS` was set in the *spawned worker subprocesses'* env but not the test process's own `os.environ`, so the test's own `restore_visible()` nudge silently used the 1200s production default instead of the test's 5s override — fixed via `os.environ.setdefault(...)` at module import time, before `celery_app` is imported (same pattern as `conftest.py`'s `DATABASE_MAX_POOL_SIZE`). (b) The worker subprocess's `stdout` was only read up to the "ready" line and then never drained again — `subprocess.PIPE` has a bounded OS buffer, and Celery's own `--loglevel=info` output can fill it over a test's runtime, at which point the *worker process itself* blocks on its own stdout write, stalling its whole event loop. Fixed with a background thread that continuously drains stdout for each worker's full lifetime, not just its startup phase — standard subprocess hygiene, not test-specific, and a real, separate cause of flakiness from Findings 1–3 above. (c) A redelivered message re-executes a task from scratch with its *original* arguments — Celery doesn't "resume" a task, it restarts it — so an early version of the test used a 30s probe-task sleep with only a 25s redelivery wait, failing every time even when the mechanism worked correctly. Fixed by right-sizing both (8s sleep, 30s redelivery wait).

**SSE ingest-progress checkpoint (§21 Phase 3) — the last unmet Phase 3 acceptance criterion, now closed.** Real design decisions made explicitly before writing any code, not defaulted into:
- **Mechanism: apps/core polls apps/brain's existing `GET /segment` status endpoint on an interval, not Postgres LISTEN/NOTIFY or a Redis pub/sub channel.** `segmentation_jobs` only ever changes 2–3 times across a job's whole lifetime (`QUEUED → PROCESSING →` terminal), so a ~2s poll costs nothing against jobs running tens of seconds to a couple of minutes. LISTEN/NOTIFY was rejected specifically because Neon's pooled connection string doesn't support it — it would need a dedicated, non-pooled connection held open per concurrent SSE stream, fighting the tight-pool discipline enforced everywhere else in this codebase (Hikari capped at 5). A Redis pub/sub channel was rejected as a new use of Redis beyond Celery's existing broker role, for the same "don't add infra a state-table poll already covers" reasoning that cut RabbitMQ entirely.
- **Location: apps/core, not apps/brain.** `V15`'s own migration comment already establishes apps/core has zero DB grant on `segmentation_jobs` and learns status only via brain's HTTP endpoint — SSE reuses that boundary rather than reopening it. The alternative (apps/brain hosting a client-facing SSE endpoint directly) would have required standing up real JWT verification in Python for the first time, cutting against blueprint's "Spring owns identity entirely" rule; not worth it for this feature.
- **A real, previously-nonexistent gap this checkpoint had to close, not just SSE on top of existing plumbing: nothing before this could actually trigger segmentation from a real client path.** `apps/core` had no HTTP client to `apps/brain` at all, and `apps/web` never referenced `/segment` — only a direct, `BRAIN_SERVICE_TOKEN`-bearing call to brain's own POST endpoint could start a job, which a browser can never make. `SourceController` now has a real `POST /api/v1/sources/{id}/segment` proxy (gated on `source:upload` — triggering segmentation is part of the ingest pipeline the uploader sets in motion, not a new trust boundary) alongside the new `GET /api/v1/sources/{id}/segment/stream` SSE endpoint (gated on a new `source:read` capability, below).
- **Auth: plain Bearer-JWT, not native `EventSource` + a URL-embedded ticket.** Native `EventSource` can't send the `Authorization` header this project's access-token model requires (JS-memory-only, never a cookie or a query param) — the frontend is expected to use `fetch()` with manual `text/event-stream` parsing instead, so the SSE endpoint needs no new auth mechanism beyond what Spring Security already enforces everywhere else. This is a state-sync stream, not a durable event-log stream: `segmentation_jobs` holds current status only, not a transition history, so there is deliberately no `Last-Event-ID`/replay mechanism — a reconnect just gets a fresh snapshot immediately, which is all there is to get.

It deliberately does not re-prove the cross-service wire contract — that's apps/brain's own job (`test_segment_source.py`, `test_segmentation_task.py`) plus this checkpoint's own one-time live check below. `secrets.BRAIN_SERVICE_TOKEN` (already an existing repo secret, reused from `ci-brain.yml`) was added to `ci-core.yml` so these tests actually run in CI rather than perpetually skip — no other CI wiring was needed, since the real apps/brain is never contacted from this job.

Second, separate finding surfaced by the same test: `SegmentationService`'s own `catch (IOException e)` block (for a client disconnecting mid-`send()`) used to also call `emitter.completeWithError(e)` — but Spring's `ResponseBodyEmitter` machinery already completes the `AsyncContext` with an error itself the moment `send()` fails this way, and calling `completeWithError` again threw `IllegalStateException` ("A non-container (application) thread attempted to use the AsyncContext after an error had occurred"). ## Standing principles (do not violate these without asking)

1. **The system must be demoable at every commit.** Don't leave the stack in a broken state overnight.
2. **Deterministic core, probabilistic edge.** Anything a parser, typechecker, or solver can decide must not be decided by an LLM. If you're about to have a model output something that determines correctness (not just a draft/candidate), stop and ask.
3. **One trust boundary, three enforcement layers** for tenant isolation: gateway → application (`TenantConnectionPreparer` AOP setting the RLS GUC per-transaction + `@PreAuthorize`) → database (RLS, `FORCE`d, fail-closed). All three, always. Note: there is no JPA/Hibernate anywhere in `apps/core` — it's `JdbcTemplate` throughout, so "Hibernate `@Filter`" (as blueprint §10.9's diagram depicts for Layer 2) does not apply to this codebase; Layer 2 is the AOP described above, not a Hibernate filter.
4. **Every LLM output is untrusted input** — including, especially, when it originates from a document the user uploaded. Never concatenate document text into a system prompt.
5. **Prefer deleting a technology over adding one.** If a task seems to need a new piece of infrastructure, check the "explicitly deferred" list below first — it's probably already been considered and rejected for now.

## Non-negotiable engineering rules

- **Idempotency:** every mutating endpoint accepts `Idempotency-Key`. Every response carries `X-Request-Id`.
- **Tenant isolation:** every tenant-scoped table has `org_id` and an RLS policy from the moment it's created — not retrofitted later. Its repository must implement `TenantScopedRepository` (`apps/core/.../platform/tenancy/`), which `TenantIsolationArchitectureTest` enforces at build time: every public method must be `@Transactional`, and no raw `DataSource`/`Connection` field is allowed. This proves the precondition for isolation, not isolation itself — the actual guarantee is still the RLS policy + `TenantConnectionPreparer`, so write and test each new repository's isolation behavior for real, the ArchUnit rule alone isn't sufficient.
- **No `localStorage`/`sessionStorage` for tokens.** Access tokens live in JS memory only. Refresh tokens are `HttpOnly` cookies.
- **Migrations are immutable once merged.** Corrections are new migrations, never edits to old ones. Use expand/contract for anything destructive.
- **No raw SQL string concatenation, ever.** Parameterized queries only, in both Java and Python.
- **Extraction/compiler output must cite a verbatim source span.** If a candidate obligation's span text doesn't literally appear in the source segment, discard it — don't try to "fix" or reinterpret it.
- **Prompts are versioned files, not inline strings.** Once Phase 4 starts, every prompt lives in `brain/prompts/` with a version and is never edited in place — bump the version.
- **Every LLM call records `model_id`, `prompt_version`, cost, and latency.** Without this, nothing about the AI pipeline is reproducible or debuggable later.
