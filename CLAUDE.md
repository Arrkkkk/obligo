## What this project is

Obligo compiles natural-language obligations (from contracts, email, transcripts) into a typed, formally verifiable intermediate representation, detects contradictions between obligations using an SMT solver (Z3), and monitors each obligation against real-world evidence until it's fulfilled or breached.

The differentiator is the compiler (LLM candidate extraction → Lark grammar parse → semantic typecheck) and the verifier (Z3 lowering + unsat-core explanation). Everything else in the stack exists to support those two things. If a proposed change doesn't serve the compiler, the verifier, or making them demoable, treat it with suspicion.

## Local dev environment — DEVIATION FROM BLUEPRINT, READ THIS FIRST

**No Docker on the local machine**, by deliberate choice (not a temporary gap — don't try to "fix" this by installing Docker). This changes how Phase 1 and beyond are executed locally:

- **Postgres:** not run locally. Use a **Neon free-tier branch** (with the `pgvector` extension enabled) as the dev database. Connection string goes in `.env` (git-ignored), never committed.
- **Redis:** not run locally. Use **Upstash's free-tier Redis** (HTTPS/REST-based, no local process needed).
- **The three services run natively**, not in containers: Spring via `./gradlew bootRun`, FastAPI via `uvicorn` in a venv, Next.js via `npm run dev`.
- **Dockerfiles and `compose.yml` still get written** per the blueprint — they're needed for CI image builds (§20.4) and eventual deployment (§20.5) — but they are **not exercised locally** and are not a dependency for local development to work. Do not block any Phase 1 task on "the Compose stack running locally," because it won't be, by design.
- **`make dev` in this project means:** start Spring, start FastAPI, start Next.js natively, pointed at the cloud Postgres/Redis — not `docker compose up`. Write the Makefile target accordingly.
- Docker becomes actually relevant again around Phase 9 (deployment) or whenever CI needs to build and push real images — not before.

## Standing principles (do not violate these without asking)

1. **The system must be demoable at every commit.** Don't leave the stack in a broken state overnight.
2. **Deterministic core, probabilistic edge.** Anything a parser, typechecker, or solver can decide must not be decided by an LLM. If you're about to have a model output something that determines correctness (not just a draft/candidate), stop and ask.
3. **One trust boundary, three enforcement layers** for tenant isolation: gateway → application (`TenantConnectionPreparer` AOP setting the RLS GUC per-transaction + `@PreAuthorize`) → database (RLS, `FORCE`d, fail-closed). All three, always. Note: there is no JPA/Hibernate anywhere in `apps/core` — it's `JdbcTemplate` throughout, so "Hibernate `@Filter`" (as blueprint §10.9's diagram depicts for Layer 2) does not apply to this codebase; Layer 2 is the AOP described above, not a Hibernate filter.
4. **Every LLM output is untrusted input** — including, especially, when it originates from a document the user uploaded. Never concatenate document text into a system prompt.
5. **Prefer deleting a technology over adding one.** If a task seems to need a new piece of infrastructure, check the "explicitly deferred" list below first — it's probably already been considered and rejected for now.
6. **Property-based tests over code that touches real extracted or quoted document text must vary semantic/syntactic complexity, not just surface form, before their coverage counts as adequate.** Added after this exact blind spot cost real time twice, independently, in Phase 4: the IR-Compiler checkpoint's trailing-period bug (hypothesis-generated structural variation — units, amounts, arbitrary trigger text — plus hand-picked textbook phrasings, both passed clean while shipping a silent corruption on a realistic trailing sentence-period) and the leading-subordinate-clause grounding-fix checkpoint's bug (`test_ground.py`'s `NESTED_FIELD_NOT_IN_SPAN` cases and its grounding-invariant hypothesis property both vary only surface form — arbitrary alphabet strings, unrelated fabricated phrases — never real clause-structure complexity like a sentence-fronting subordinate clause). Before trusting a property/hypothesis suite's coverage for anything downstream of real extracted or quoted document text, ask explicitly: does this generator vary semantic/syntactic complexity, or only surface form? A generator that only varies the latter can pass exhaustively while missing an entire failure class — and, for anything whose "function under test" is actually an LLM's behavior rather than pure code (the grounding-fix case, not the IR-Compiler case), no property generator can close the gap at all; only sampling real model output (cassette or live) can.

7. **A verification script's output is not evidence until the script has been checked against a known-answer case.** Added after this failure class cost real time **four** times in a single work session, always the same shape: a lookup or regex **silently defaults to a wrong-but-plausible answer for an input it does not handle**, and the output looks reasonable enough to survive casual inspection. The four, all from the gold-set consolidation pass: (1) §19.7's OCR detector written `[a-hj-z]` to exclude the one-letter words *a* and *I* — but that class still contains `a`, so it matched "in a"/"of a" and fired on **11 of 18 items at a 100% false-positive rate with zero true positives**; (2) a coordination detector whose `{0,140}` window between two modals **missed the very sentence it was written to verify** (`C14-076`'s splitting sentence, ~148 chars), so a "verified" claim rested on a detector that never saw the case; (3) a party-subject classifier anchored `^\s*(?:that\s+)?` that missed `", Antares or its Subcontractor shall provide"` (leading comma) and `"that, if AMAG …, AMAG shall"` (subject not first), producing a 25.7%/48.5% split that was pure detector noise; (4) a verb-pair classifier using `MAP.get(v, '?')`, where two *unmapped* verbs both return `'?'` and compare equal — so `construed + enforced`, a governing-law clause that is not an obligation at all, was reported as a same-taxonomy-verb doublet. **A sibling instance in shell rather than in Python, recorded because the mechanism is distinct and worth finding on its own: a pipeline's exit code is the exit code of the LAST command in the pipe, not of the one you care about.** `pytest ... 2>&1 | tail -4` reported `exit=0` for a run that pytest itself had failed — `tail` succeeded, so the pipeline succeeded, and the real signal was discarded before anything could read it. The failure was visible only in pytest's own summary line, which is prose rather than a status code. Same shape as the four detector cases below: a status that looks authoritative while measuring the wrong thing. **A SECOND instance of the identical rule, found 2026-08-24 during the gold-set recording run — recorded because it generalises the guard beyond pipes.** The exit status of a compound command is that of its LAST component whatever the operator joins them — `;` no less than `|`. A backgrounded `python … > run.log 2>&1; echo "EXIT=$?"` was reported by the harness as **exit code 0** for a script that had in fact exited **1**: the trailing `echo` succeeded, so the wrapping shell succeeded. The job-completion notification therefore announced a clean run for a recording that had crashed mid-set on an HTTP 400, and the correct `EXIT=1` the `echo` itself printed was sitting in the log with nothing reading it, because the status line already said 0. It was caught only by reading the log rather than trusting the reported status — the same move that catches every case above. **A THIRD instance, found 2026-08-25 while pushing the v0.33 scoring work — and it is the one that falsifies this principle's own stated remedy, so the remedy below is corrected rather than merely annotated.** `git push ... 2>&1 | tail -5; echo "PUSH_EXIT=${PIPESTATUS[0]}"` printed **`PUSH_EXIT=`** — empty. Not a wrong number: **no number at all**, which reads as benign at a glance and is arguably worse than a wrong one, since there is no value to look twice at. **Cause: `PIPESTATUS` is a bashism.** This machine's shell is **zsh** (see the Environment block), where the array is `$pipestatus`, **lower-case and 1-indexed**; `${PIPESTATUS[0]}` is simply an unset variable and expands to the empty string with no error. Verified by execution rather than from memory, per this principle's own discipline: `false | true; echo "${PIPESTATUS[0]}"` → `''`, while `${pipestatus[1]}` → `1`.

**The mechanism is distinct from the two above and that is why it is its own instance.** Those two were *"the status came from the wrong command."* This is *"the status expression evaluated to nothing,"* a **shell-dialect** mismatch — the same family (a status that looks authoritative while measuring nothing) reached through a third door. It confirms the family recurs across **shells**, not only across tools and operators.

**CORRECTED REMEDY — the previous wording recommended `${PIPESTATUS[0]}` unconditionally, and on this repo's own default shell that recommendation is silently broken.** Any scripted check whose verdict comes from an exit code must not pipe OR postfix the command being judged. In order of preference: **(a) capture to a file and read `$?` directly on the very next line** — portable, works in every shell, and the only option with no dialect hazard; **(b) let the judged program be the last thing the compound command runs**; **(c) a pipe-status array ONLY with the shell confirmed** — `${pipestatus[1]}` in zsh, `${PIPESTATUS[0]}` in bash — and never assume which is in play. **(d) Best of all, where the thing being judged has a durable artifact: verify the outcome directly rather than through any status** — the push above was confirmed instead by diffing local `HEAD` against `git ls-remote`, which cannot be fooled by a dialect at all.

The pipeline instance was found 2026-08-22 while checking the full suite during the gold-set harness build; the compound-command one 2026-08-24 during the stage-4 recording run; this one 2026-08-25 during the v0.33 push. **A dated RECURRENCE of the compound-command sibling, 2026-09-05 during the F13/Decision-3 ruling session — recorded as a recurrence, not a new principle, because the mechanism is exactly the one already described.** A backgrounded `pytest -q > log 2>&1; echo "EXIT=$?"; tail -20 log` was announced by the harness's job-completion notification as **"exit code 0"**, and the log's own trailer read `[exited with code 0]`, for a run that had **1 failed, 493 passed, 53 skipped**. The trailing `tail` succeeded, so the wrapping shell succeeded; the correct `EXIT=1` the `echo` itself printed was sitting on the log's **first line** with nothing reading it. Caught only by reading the log rather than trusting the reported status — and the failure it hid was a real one that mattered (a known-answer reproduction test pinning a published figure the session's own ruling legitimately moved). **The remedy already stated above is the one that would have prevented it: capture to a file and read `$?` on the very next line, and do not postfix the command being judged.** **AN EIGHTH ENTRY, 2026-09-17 during the §8.8.4 amendment session — the compound-command sibling again, and this time it misreported a CI verdict rather than a test run.** A backgrounded `gh run watch <id> --exit-status > log 2>&1; echo "WATCH_EXIT=$?"` was announced by the harness's job-completion notification as **"completed (exit code 0)"**, and the log's own trailer read `[exited with code 0]`, for a CI run that had **FAILED**. `gh run watch --exit-status` did its job and returned 1 — **`WATCH_EXIT=1` is sitting in the log, on its own line, with nothing reading it** — but the trailing `echo` succeeded, so the wrapping shell succeeded. Identical mechanism to the 2026-08-24 and 2026-09-05 instances; the new part is the **domain**, a remote CI conclusion rather than a local test exit, which is the one place a false green is most likely to be taken at face value and shipped. **It was caught only because the run's status was polled separately via `gh run view` rather than read off the notification — sequencing, not discipline.** The remedy already stated above is the one that would have prevented it: capture to a file and read `$?` on the very next line, do not postfix the command being judged — or, best here, verify the outcome directly (`gh run view --json conclusion`), which cannot be fooled by a wrapper at all.

*(The list now holds **eight**: four detector cases plus four exit-code/status siblings — the 2026-08-25 `PIPESTATUS`-in-zsh one being the seventh and the 2026-09-17 `gh run watch` one the eighth. Each count is arrived at by **counting the list**, never by incrementing the previous claim: an earlier session called the 2026-09-05 recurrence the "seventh" when the list in fact held six, which is how a running tally drifts if it is trusted instead of recomputed.)*

**The discipline: before trusting a detector's counts, run it against cases whose answer is already established** — a previously measured ground truth (§2.4's six known OCR segments exposed (1)), or the specific case the detector was written to find (checking flagged context against the known sentence exposed (2)), or simply reading the flagged and unflagged examples rather than only the totals (exposed (3) and (4)). All four were caught by looking at real output against known cases, and none would have been caught by re-reading the pattern. This is the sibling of Standing Principle 6: 6 is about generators that vary only surface form, 7 is about detectors that fail silently on unhandled input — and both say the same thing, that a clean-looking result is not evidence until you have checked what it does on a case whose answer you already know.

## Non-negotiable engineering rules

- **Idempotency:** every mutating endpoint accepts `Idempotency-Key`. Every response carries `X-Request-Id`.
- **Tenant isolation:** every tenant-scoped table has `org_id` and an RLS policy from the moment it's created — not retrofitted later. Its repository must implement `TenantScopedRepository` (`apps/core/.../platform/tenancy/`), which `TenantIsolationArchitectureTest` enforces at build time: every public method must be `@Transactional`, and no raw `DataSource`/`Connection` field is allowed. This proves the precondition for isolation, not isolation itself — the actual guarantee is still the RLS policy + `TenantConnectionPreparer`, so write and test each new repository's isolation behavior for real, the ArchUnit rule alone isn't sufficient.
- **No `localStorage`/`sessionStorage` for tokens.** Access tokens live in JS memory only. Refresh tokens are `HttpOnly` cookies.
- **Migrations are immutable once merged.** Corrections are new migrations, never edits to old ones. Use expand/contract for anything destructive.
- **No raw SQL string concatenation, ever.** Parameterized queries only, in both Java and Python.
- **Extraction/compiler output must cite a verbatim source span.** If a candidate obligation's span text doesn't literally appear in the source segment, discard it — don't try to "fix" or reinterpret it.
- **Prompts are versioned files, not inline strings.** Once Phase 4 starts, every prompt lives in `brain/prompts/` with a version and is never edited in place — bump the version.
- **Every LLM call records `model_id`, `prompt_version`, cost, and latency.** Without this, nothing about the AI pipeline is reproducible or debuggable later.
