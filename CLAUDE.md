## What this project is

Obligo compiles natural-language obligations (from contracts, email, transcripts) into a typed, formally verifiable intermediate representation, detects contradictions between obligations using an SMT solver (Z3), and monitors each obligation against real-world evidence until it's fulfilled or breached.

The differentiator is the compiler (LLM candidate extraction → Lark grammar parse → semantic typecheck) and the verifier (Z3 lowering + unsat-core explanation). Everything else in the stack exists to support those two things. If a proposed change doesn't serve the compiler, the verifier, or making them demoable, treat it with suspicion.

## Local dev environment — DEVIATION FROM BLUEPRINT, READ THIS FIRST

**No Docker on the local machine**, by deliberate choice (not a temporary gap — don't try to "fix" this by installing Docker). This changes how Phase 1 and beyond are executed locally:

- **Postgres:** not run locally. Use a **Neon free-tier branch** (with the `pgvector` extension enabled) as the dev database. Connection string goes in `.env` (git-ignored), never committed.
- **Redis:** not run locally. Use **Upstash's free-tier Redis** (HTTPS/REST-based, no local process needed).
- **The three services run natively**, not in containers: Spring via `./gradlew bootRun`, FastAPI via `uvicorn` in a venv, Next.js via `npm run dev`.
- **Dockerfiles and `compose.yml` still get written** per the blueprint — they're needed for CI image builds (§20.4) and eventual deployment (§20.5) — but they are **not exercised locally** and are not a dependency for local development to work. Do not block any Phase 1 task on "the Compose stack running locally," because it won't be, by design.
- **`make dev` in this project means:** start Spring, start FastAPI, start Next.js natively, pointed at the cloud Postgres/Redis — not `docker compose up`. Write the Makefile target accordingly.
- Docker becomes actually relevant again around Phase 9 (deployment) or whenever CI needs to build and push real images — not before.

Two real corrections landed during scoping, both worth keeping on record since they shaped the final lowering: (1) an early worked example used an interval-*intersection* framing for what makes two obligations conflict — caught as wrong before code existed, because a `MUST DELIVER` in January and a `MUST_NOT DELIVER` in June never intersect and are trivially satisfiable, while two obligations whose windows *do* intersect can still be either SAT (partial overlap) or UNSAT (full containment) depending on direction. - **The conflict condition actually implemented is residual-emptiness, not intersection and not subset-in-either-direction as a standalone rule** — `docs/VERIFIER.md`'s own "The conflict condition" section has the full derivation. For the two-obligation case this reduces to a clean, testable statement: `MUST(W)`/`MUST_NOT(P)` is unsat iff `W ⊆ P`. Proven two ways: worked fixtures (`tests/verifier/test_verify.py`'s Example A — containment, UNSAT; Example A′ — partial overlap, SAT; Example S/T — prohibition nested inside a wider duty window, SAT because January and March survive outside the carved-out freeze; Example B — a genuine 3-way conflict where every pair is individually SAT and only the group together is UNSAT, the concrete justification for solving candidate sets rather than pairs) and a hypothesis property checking the real Z3 verdict against an independent, pure-Python set-containment oracle across hundreds of generated interval pairs (`test_must_must_not_unsat_iff_duty_window_is_subset_of_prohibition`).
- **Act keys are why two `MUST`s never conflict with each other regardless of their windows, by construction, not by a runtime check** — every MUST/SHOULD gets its own fresh Z3 `Int`; two duties to perform the same kind of act are two acts, not a shared performance. This is what keeps ordinary supersession (a later amendment's new deadline) from being read as a fabricated contradiction, and it's pinned as its own hypothesis property (`test_must_must_never_conflicts_regardless_of_windows`, and symmetrically for `MUST_NOT`/`MUST_NOT`) rather than left implicit in the worked examples alone.
- **The action-antagonism table (`RETAIN`→`DELETE`, `WITHHOLD`→`DISCLOSE`) closes the product's own headline example** ("a retention policy contradicted a deletion promise," this file's §1.3 vision) — `DELETE` and `RETAIN` are different actions in the closed 34-verb taxonomy, so a literal `MUST RETAIN`/`MUST DELETE` pair shares no act key and a plain modal check never fires on it without this table. Deliberately one-directional, not a symmetric pair, and that's a real semantic distinction, not an oversight: `RETAIN`/`WITHHOLD` describe a continuous state held throughout a window (the same shape as a `MUST_NOT`'s own forbidding window), `DELETE`/`DISCLOSE` describe a point-in-time act — "must delete by March 1" does not forbid retaining right up until the deletion, so the reverse direction is deliberately absent and pinned as its own regression test (`test_antagonism_is_not_symmetric_must_not_retain_does_not_imply_prohibition_on_delete`, `test_delete_must_never_implies_a_prohibition_on_retain`). Seeded strictly with exactly these two pairs, matching `ir_compile.py`'s own "strict over loose" posture — plausible-but-arguable pairs (`TERMINATE`/`MAINTAIN`) are deliberately left out.
- **Explanation is deterministic, template-based per finding kind, with zero LLM calls anywhere in the module — approved as proposed, without qualification, before implementation started.** Every fact in a rendered sentence is read directly from the minimal core's own labels (obligor name, action, object phrase, real dates); Standing Principle 2 and blueprint §6.7's own "the claim comes from the core... never let the model invent the reason" apply directly, and the span-grounding Tier-C precedent (`"shall"` → `"shall not"` inverting a clause's meaning at ~2% edit distance) is the concrete reason a polish step isn't added even as an option in this checkpoint.
- **Conditions lower to plain Z3 `Bool`s asserted as bare literals, not used to guard the modal/window facts** — a simplification found during implementation, not part of the original scoping proposal (which described `Implies`-guarded assertions): since condition literals are already assumed true per the approved design, guarding the window facts by them changes no verdict, only adds unused machinery. Same atom text across two different obligations' conditions is the same Z3 variable, which is what lets `IF "X"` in one obligation and `IF NOT "X"` in another genuinely contradict each other (`CONDITION_CONTRADICTION`, `tests/verifier/test_verify.py::test_condition_contradiction_without_any_modal_conflict`) — and, separately, what lets a `.cond` fact and a `.window`/`.prohibition` fact be found as two *independent* minimal cores in one solve when both are genuinely present (`test_condition_contradiction_isolated_no_temporal_overlap_at_all`, which real-world both contradicts on conditions and conflicts modally, and the multi-core enumeration correctly reports both).
- **Multiple independent conflicts in one candidate group are enumerated via Z3 assumptions, not `push`/`pop`** — another implementation-level refinement of the scoping proposal's conversational description. Every fact is asserted as `Implies(selector, constraint)`, with the selector passed as an *assumption* to `solver.check()` per call rather than permanently asserted true; this is what makes deletion-based minimization and multi-core search both possible by varying which selectors are active per call, reusing one `Solver` object throughout a group's search, bounded at 5 cores total and a 120s timeout (`Z3_TIMEOUT_MS`, matching blueprint §4.2's own constant) that surfaces as `VerificationResult.timed_out_groups`, never a silently-claimed SAT.
- **`TEMPORAL_IMPOSSIBILITY` (an obligation's own reversed `DURING` bounds) is detected in pure Python, not through Z3** — `intervals.is_empty()` on the obligation's own window, checked before candidate grouping even runs. Routing a self-contained defect through the solver would risk it being misattributed to whichever obligation it happened to be grouped with; detecting it separately also means a `TEMPORAL_IMPOSSIBILITY`-flagged obligation needs no candidate partner at all to be caught, unlike every other finding kind.

- **THE FINDING THAT MATTERS MOST: there is no evidence the rule-discovery rate is tapering, and the honest answer at n=2 is "we cannot tell."** Bumps per item went **up**, 0.50 → 1.00 (ratio 2.00, exact p = 0.168, 95% CI on the ratio **[0.65, 6.11]**); a Poisson regression over the 17-item sequence gives slope **+0.0322/item**, 95% CI on the multiplier **[0.924, 1.159]**, LR χ² = 0.321, **p > 0.05**. Compatible with anything from a 7.6% decline to a 15.9% rise per item. **Every planning figure below therefore assumes the non-tapered batch-2 rate.** A taper would be a welcome surprise, never a premise. A document-saturation model was proposed and **falsified on this data** (batch 1: 7 documents → 5 bumps; batch 2: **3** documents → **8**) and is recorded in guideline §19.2 so it is not re-proposed.
- **Batch 1's ~40% structurally-uncompilable finding is confirmed by batch 2, not refuted: 7 of 18 locked items (38.9%, 95% CI [20.3%, 61.4%]), or 9 of 18 counting `corpus_artifact_in_span` spans.** Consequence, and it is a scope finding about Phase 4's own acceptance bar rather than an extraction-quality one: **criterion 2's ceiling over its stated all-items denominator is ~39–61% at every point in the measured interval, so ≥80% is arithmetically unreachable there.** The recommended fix is §11's existing treatment for criterion 1b — dual-report over all items and over `len(known_gaps) == 0` items, with the ceiling stated in advance. **Recorded in guideline §9 as RECOMMENDED and explicitly NOT in force**: it is a blueprint §21 amendment and needs its own decision.
- **The target size was audited on request and downgraded from a recommendation to a working figure.** An earlier draft of this recalibration argued "100 is approximately the minimum defensible size" with the same confidence as the measured numbers. It does not deserve that: the argument depends on (1) an **unmeasured** true fully-correct rate — required scoreable N is 25 at a true 95%, 54 at 90%, 87 at 88%, **230 at 85%**, and no rate has ever been computed; (2) a gap-rate interval too wide to discriminate — 100 annotated items yields anywhere from **39 to 80** scoreable, straddling the threshold; and (3) a Wilson-interval independence assumption **the data violates**, since items cluster by segment (batch 2's 8 items came from 4 segments, 3 from `C02-021` alone), which makes every required-N figure an underestimate. **100 stands because it is the existing spec and nothing yet justifies changing it, not because it was derived.** See guideline §19.5.
- **Planning figures, with their status stated rather than implied.** The cost model `min/item = (adjudications/item × 18.2) + 7` is an **assumption**: a two-parameter model fitted to two data points, zero residual degrees of freedom, so it **cannot fail to fit** — a structural story about where time goes, not a validated law. On it: **remaining 82 items ≈ 38 h at the non-tapered rate, contingency 55 h; total to a scored criterion-2 number ≈ 62–73 h** (consolidation 6 · harness build and run 4–8 · 82 items 38 · freeze-time conforming 6 · §7 held-out 8–15). **The harness, held-out, and per-re-check components are guesses with no measured basis** and are labelled as such in guideline §19.6. An unquantified `K ≥ 4 → REDESIGN` branch in §7 would reset most of it.
- **Batch 2 paused at 8 of 10, and the pause is the decision this checkpoint actually makes.** Two items remain undrawn. They are cheap (~55 min) but cannot answer anything — adding 2 items to a 17-item sequence narrows the trend interval by ~5%. The consolidation pass instead closes, in one sitting: the **seven open decisions** (five rules at `DEFAULT, PENDING CONFIRMATION` — §15 v0.4, §16 v0.5, §17 v0.6, §8.3.1 v0.23, §8.8 v0.24 — plus `C03-02` and `C11-01` at `DRAFTER_JUDGMENT_PENDING_REVIEW`), **three of which have been open since before batch 1 existed**; **154 outstanding item × rule re-checks** (fifteen of the 18 locked items were annotated against a since-changed ruleset; `E01-01` has never been checked against 13 later rule versions). *Corrected from the 127 first recorded in this entry and in guideline v0.26 — both counted version bumps rather than rules, and v0.16, v0.17 and v0.21 each introduced two; corrected at guideline v0.27.* Also: `SUMMARY.md`'s single-version claim, and a §7 amendment for a held-out draw against an 8-item batch. §10's conforming step is mandatory before the freeze regardless — deferring it to the freeze would face an estimated ~390 re-checks in one tangle instead of 154 now. **The freeze stays after batch 3**, unchanged.
- **Three false claims in the guideline were corrected at v0.26**, all pre-existing: its header read *"No items have been annotated against this document yet"* from v0.1 through v0.25 (18 have, since 2026-08-19); and the **v0.15** and **v0.17** changelog entries each claimed to be "the version batch 1 is annotated under," contradicting each other — batch 1's items in fact stamp **six** versions. Both changelog claims are struck in place with a superseded marker rather than deleted. `apps/brain/evals/goldens/batch01/SUMMARY.md` carries the same defect and is deliberately **not** fixed here: it is consolidation-pass work.
- **Consolidation pass begun: the mechanical sweep clears 139 of the 154 re-checks, leaving 15 for the reviewer** (guideline §19.7). Detectors are deliberately high-recall/low-precision — a false positive costs minutes, a false negative leaves a silent conformance gap. This cuts the pass's re-check component from ~3.2 h to well under an hour, so the ~6 h estimate becomes ~2.5–3 h. **A detector bug was found and fixed mid-sweep and is recorded rather than quietly corrected:** §2.4's OCR detector was written `[a-hj-z]` intending to exclude the one-letter words *a* and *I*, but that class still contains `a`, so it matched "in a"/"of a" and fired on 11 of 18 items across 8 documents at a **100% false-positive rate with zero true positives**. §2.4's own measured ground truth — 6 segments, all in `C11` — is what exposed it. Same shape as the trailing-period and leading-clause bugs already on record: a check that passes casual inspection while being wrong on every real case.
- **The highest-value next action is not annotation.** Building the scoring harness and running it against the **18 already-locked items** requires no further annotation and is the cheapest way to learn which column of the required-N table this project is in. At a true ~95% the set could stop near 50 items; at ~85% no achievable N certifies criterion 2 and it must be restated instead. Target size and criterion-2 framing are both deferred to that number.
- **Tripwire, recorded because the variable that drives everything is currently unrecorded.** Adjudications per item per batch must be logged going forward — today it is recoverable only by mining transcripts, which is how this entire checkpoint had to be produced. **If batch 3 produces ≥15 bumps over 10 items (adj/item ≥ 1.50), the 38 h plan is broken and target size re-opens.** Because discovery is draw-dependent and high-variance, evaluate against the cumulative rate across batches 2–3, never batch 3 alone.

## Standing principles (do not violate these without asking)

1. **The system must be demoable at every commit.** Don't leave the stack in a broken state overnight.
2. **Deterministic core, probabilistic edge.** Anything a parser, typechecker, or solver can decide must not be decided by an LLM. If you're about to have a model output something that determines correctness (not just a draft/candidate), stop and ask.
3. **One trust boundary, three enforcement layers** for tenant isolation: gateway → application (`TenantConnectionPreparer` AOP setting the RLS GUC per-transaction + `@PreAuthorize`) → database (RLS, `FORCE`d, fail-closed). All three, always. Note: there is no JPA/Hibernate anywhere in `apps/core` — it's `JdbcTemplate` throughout, so "Hibernate `@Filter`" (as blueprint §10.9's diagram depicts for Layer 2) does not apply to this codebase; Layer 2 is the AOP described above, not a Hibernate filter.
4. **Every LLM output is untrusted input** — including, especially, when it originates from a document the user uploaded. Never concatenate document text into a system prompt.
5. **Prefer deleting a technology over adding one.** If a task seems to need a new piece of infrastructure, check the "explicitly deferred" list below first — it's probably already been considered and rejected for now.
6. **Property-based tests over code that touches real extracted or quoted document text must vary semantic/syntactic complexity, not just surface form, before their coverage counts as adequate.** Added after this exact blind spot cost real time twice, independently, in Phase 4: the IR-Compiler checkpoint's trailing-period bug (hypothesis-generated structural variation — units, amounts, arbitrary trigger text — plus hand-picked textbook phrasings, both passed clean while shipping a silent corruption on a realistic trailing sentence-period) and the leading-subordinate-clause grounding-fix checkpoint's bug (`test_ground.py`'s `NESTED_FIELD_NOT_IN_SPAN` cases and its grounding-invariant hypothesis property both vary only surface form — arbitrary alphabet strings, unrelated fabricated phrases — never real clause-structure complexity like a sentence-fronting subordinate clause). Before trusting a property/hypothesis suite's coverage for anything downstream of real extracted or quoted document text, ask explicitly: does this generator vary semantic/syntactic complexity, or only surface form? A generator that only varies the latter can pass exhaustively while missing an entire failure class — and, for anything whose "function under test" is actually an LLM's behavior rather than pure code (the grounding-fix case, not the IR-Compiler case), no property generator can close the gap at all; only sampling real model output (cassette or live) can.

7. **A verification script's output is not evidence until the script has been checked against a known-answer case.** Added after this failure class cost real time **four** times in a single work session, always the same shape: a lookup or regex **silently defaults to a wrong-but-plausible answer for an input it does not handle**, and the output looks reasonable enough to survive casual inspection. The four, all from the gold-set consolidation pass: (1) §19.7's OCR detector written `[a-hj-z]` to exclude the one-letter words *a* and *I* — but that class still contains `a`, so it matched "in a"/"of a" and fired on **11 of 18 items at a 100% false-positive rate with zero true positives**; (2) a coordination detector whose `{0,140}` window between two modals **missed the very sentence it was written to verify** (`C14-076`'s splitting sentence, ~148 chars), so a "verified" claim rested on a detector that never saw the case; (3) a party-subject classifier anchored `^\s*(?:that\s+)?` that missed `", Antares or its Subcontractor shall provide"` (leading comma) and `"that, if AMAG …, AMAG shall"` (subject not first), producing a 25.7%/48.5% split that was pure detector noise; (4) a verb-pair classifier using `MAP.get(v, '?')`, where two *unmapped* verbs both return `'?'` and compare equal — so `construed + enforced`, a governing-law clause that is not an obligation at all, was reported as a same-taxonomy-verb doublet. **A sibling instance in shell rather than in Python, recorded because the mechanism is distinct and worth finding on its own: a pipeline's exit code is the exit code of the LAST command in the pipe, not of the one you care about.** `pytest ... 2>&1 | tail -4` reported `exit=0` for a run that pytest itself had failed — `tail` succeeded, so the pipeline succeeded, and the real signal was discarded before anything could read it. The failure was visible only in pytest's own summary line, which is prose rather than a status code. Same shape as the four detector cases below: a status that looks authoritative while measuring the wrong thing. **A SECOND instance of the identical rule, found 2026-08-24 during the gold-set recording run — recorded because it generalises the guard beyond pipes.** The exit status of a compound command is that of its LAST component whatever the operator joins them — `;` no less than `|`. A backgrounded `python … > run.log 2>&1; echo "EXIT=$?"` was reported by the harness as **exit code 0** for a script that had in fact exited **1**: the trailing `echo` succeeded, so the wrapping shell succeeded. The job-completion notification therefore announced a clean run for a recording that had crashed mid-set on an HTTP 400, and the correct `EXIT=1` the `echo` itself printed was sitting in the log with nothing reading it, because the status line already said 0. It was caught only by reading the log rather than trusting the reported status — the same move that catches every case above. **Any scripted check whose verdict comes from an exit code must not pipe OR postfix the command being judged** — capture to a file and read `$?` directly, use `${PIPESTATUS[0]}`, or let the judged program be the last thing the compound command runs. The pipeline instance was found 2026-08-22 while checking the full suite during the gold-set harness build; this one 2026-08-24 during the stage-4 recording run. *(These two are the fifth and sixth instances in this principle's list — four detector cases plus two exit-code siblings. Noted because a session ruling described this one as the "seventh"; the list as written holds six.)*

**The discipline: before trusting a detector's counts, run it against cases whose answer is already established** — a previously measured ground truth (§2.4's six known OCR segments exposed (1)), or the specific case the detector was written to find (checking flagged context against the known sentence exposed (2)), or simply reading the flagged and unflagged examples rather than only the totals (exposed (3) and (4)). All four were caught by looking at real output against known cases, and none would have been caught by re-reading the pattern. This is the sibling of Standing Principle 6: 6 is about generators that vary only surface form, 7 is about detectors that fail silently on unhandled input — and both say the same thing, that a clean-looking result is not evidence until you have checked what it does on a case whose answer you already know.

## Non-negotiable engineering rules

- **Idempotency:** every mutating endpoint accepts `Idempotency-Key`. Every response carries `X-Request-Id`.
- **Tenant isolation:** every tenant-scoped table has `org_id` and an RLS policy from the moment it's created — not retrofitted later. Its repository must implement `TenantScopedRepository` (`apps/core/.../platform/tenancy/`), which `TenantIsolationArchitectureTest` enforces at build time: every public method must be `@Transactional`, and no raw `DataSource`/`Connection` field is allowed. This proves the precondition for isolation, not isolation itself — the actual guarantee is still the RLS policy + `TenantConnectionPreparer`, so write and test each new repository's isolation behavior for real, the ArchUnit rule alone isn't sufficient.
- **No `localStorage`/`sessionStorage` for tokens.** Access tokens live in JS memory only. Refresh tokens are `HttpOnly` cookies.
- **Migrations are immutable once merged.** Corrections are new migrations, never edits to old ones. Use expand/contract for anything destructive.
- **No raw SQL string concatenation, ever.** Parameterized queries only, in both Java and Python.
- **Extraction/compiler output must cite a verbatim source span.** If a candidate obligation's span text doesn't literally appear in the source segment, discard it — don't try to "fix" or reinterpret it.
- **Prompts are versioned files, not inline strings.** Once Phase 4 starts, every prompt lives in `brain/prompts/` with a version and is never edited in place — bump the version.
- **Every LLM call records `model_id`, `prompt_version`, cost, and latency.** Without this, nothing about the AI pipeline is reproducible or debuggable later.
